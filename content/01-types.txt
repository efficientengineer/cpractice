## Types are about bytes, not objects

In C# an `int` is always 32 bits and a `long` always 64, by specification. In JavaScript every number is a double (plus `BigInt`). C only promises *minimum* ranges and an ordering:

```text
sizeof(char) == 1  <=  short  <=  int  <=  long  <=  long long
```

with `short` and `int` at least 16 bits, `long` at least 32, `long long` at least 64. What you actually get depends on the platform's *data model*. This site (and practically all 64-bit Linux and macOS) uses **LP64**:

| Type | Bytes | Range on LP64 | Closest C# |
|---|---|---|---|
| `char` | 1 | -128..127 or 0..255 (see below) | `sbyte` / `byte` |
| `short` | 2 | -32768..32767 | `short` |
| `int` | 4 | about ±2.1 billion | `int` |
| `long` | 8 | about ±9.2e18 | `long` |
| `long long` | 8 | about ±9.2e18 | `long` |
| `float` | 4 | ~7 significant digits | `float` |
| `double` | 8 | ~15-16 significant digits | `double` |
| any pointer | 8 | | `IntPtr` / `nint` |

> Windows uses **LLP64**: `long` is only 4 bytes there. Code that stores a pointer or a file size in a `long` breaks on Windows. This is why fixed-width types exist.

Every integer type has an `unsigned` twin with the same size: `unsigned int` (or just `unsigned`), `unsigned long`, and so on. Plain `int`, `short`, `long` are signed.

## sizeof

`sizeof` is an operator, not a function. It gives a size in bytes as a `size_t`, computed at compile time (except for variable-length arrays). Parentheses are required for a type name and optional for an expression. The expression is **not evaluated**.

```c
#include <stdio.h>

int main(void) {
    int x = 5;
    double values[10];
    printf("%zu %zu %zu\n", sizeof(int), sizeof x, sizeof(void *));
    printf("%zu\n", sizeof values);                     // 80: the whole array
    printf("%zu\n", sizeof values / sizeof values[0]);  // 10: the element count idiom
    printf("%zu\n", sizeof x++);                        // 4, and x is NOT incremented
    printf("%d\n", x);                                  // 5
    return 0;
}
```

## Fixed-width types: stdint.h

When the size matters (file formats, network protocols, hashing, bit manipulation), use `<stdint.h>`:

| Type | Meaning |
|---|---|
| `int8_t`, `int16_t`, `int32_t`, `int64_t` | exactly that many bits, signed |
| `uint8_t` ... `uint64_t` | exactly that many bits, unsigned |
| `int_least32_t`, `int_fast32_t` | at least 32 bits / the fastest such type (rarely needed) |
| `intptr_t`, `uintptr_t` | an integer big enough to hold a pointer |
| `intmax_t`, `uintmax_t` | the widest integer type |

Their limits are `INT32_MAX`, `INT32_MIN`, `UINT8_MAX`, `UINT64_MAX`, etc. Printing them portably needs `<inttypes.h>`, whose macros expand to the right `printf` letters for the platform. They are string literals, glued to the rest of the format by adjacent-literal concatenation:

```c
#include <stdio.h>
#include <stdint.h>
#include <inttypes.h>

int main(void) {
    int64_t big = INT64_MAX;
    uint8_t byte = 255;
    printf("%" PRId64 "\n", big);       // "%" "ld" "\n" on LP64
    printf("%" PRIu8 " %d\n", byte, byte);
    return 0;
}
```

> **Performance:** pick sizes by *where the value lives*. For locals, loop counters and arithmetic, use `int` (or `int32_t`): it is the size the CPU handles natively, and narrower types only add conversions. For data stored by the thousand (tile ids in a map, particle lifetimes, per-vertex colors) use the smallest type that holds the range: a 256x256 map of `uint8_t` tile ids is 64 KB and fits in the L2 cache, the same map as `int64_t` is 512 KB and doesn't. A cache line is 64 bytes, so it carries 64 `uint8_t`s or 8 `int64_t`s. The bad habit is `int64_t` (or `double`) everywhere "just in case": it halves or quarters how much useful data each memory access brings in.

## size_t and ptrdiff_t

`size_t` (from `<stddef.h>`, also pulled in by `<stdio.h>`, `<string.h>`, `<stdlib.h>`) is the unsigned type that `sizeof` yields and that `strlen`, `malloc` and `memcpy` use for sizes. On LP64 it is 64 bits. Print it with `%zu`. `ptrdiff_t` is the signed type you get by subtracting two pointers; print it with `%td`.

The classic `size_t` bug is counting down:

```c
#include <stdio.h>

int main(void) {
    const char *s = "abc";
    // for (size_t i = 2; i >= 0; i--)   // infinite: a size_t is always >= 0
    for (size_t i = 3; i-- > 0; )       // the idiom: test, then decrement
        putchar(s[i]);
    putchar('\n');
    return 0;
}
```

## char is a small integer

`char` is just a 1-byte integer type. A character literal like `'A'` is an `int` with value 65 (yes, `int`, not `char`: `sizeof('A')` is 4 in C, unlike C++). There is no separate character type, no UTF-16, no `string` class.

```c
#include <stdio.h>

int main(void) {
    char c = 'A';
    printf("%c %d\n", c, c);          // A 65
    printf("%c\n", c + 2);            // C
    printf("%d\n", '7' - '0');        // 7: digit characters are contiguous
    printf("%c\n", 'a' - 'a' + 'A');  // A: so are letters in ASCII
    return 0;
}
```

Whether plain `char` is signed is *implementation-defined*: signed on x86, unsigned on ARM. `char`, `signed char` and `unsigned char` are three distinct types. Use `unsigned char` (or `uint8_t`) for raw bytes, and plain `char` only for text.

## Floating point

`float` and `double` are IEEE 754, exactly like C#'s `float`/`double` and JS's `number` (which is a `double`). Same rounding surprises:

```c
#include <stdio.h>
#include <math.h>

int main(void) {
    double a = 0.1 + 0.2;
    printf("%.17f\n", a);                 // 0.30000000000000004
    printf("%d\n", a == 0.3);             // 0
    printf("%d\n", fabs(a - 0.3) < 1e-9); // 1: compare with a tolerance
    float f = 16777217;                   // 2^24 + 1: not representable in float
    printf("%.1f\n", f);                  // 16777216.0
    printf("%f %f\n", 1.0 / 0.0, -1.0 / 0.0);  // inf -inf (integer / 0 is UB!)
    return 0;
}
```

In general-purpose code, use `double` unless you have a reason to use `float`. Games usually *have* the reason: positions, velocities, colors and anything sent to the GPU are `float`. `printf` takes `%f` for both (a `float` argument is promoted to `double`), but `scanf` needs `%f` for `float *` and `%lf` for `double *`.

> **Performance:** a `float` is half the size of a `double`, so an array of a million particle positions takes half the memory bandwidth, and a SIMD register holds twice as many (8 floats in a 256-bit AVX register, against 4 doubles). GPUs work in `float`. The precision cost is real: a `float` has about 7 significant digits, so at 100,000 units from the origin its steps are about 0.008 units, enough to make movement jitter. Big worlds keep coordinates relative to a nearby origin (or use `double` for world position only). One trap ruins `float` code silently: an unsuffixed literal is a `double`, so `x * 0.5` converts `x` to `double`, multiplies, and converts back. Write `x * 0.5f`, and `sqrtf`, `fabsf`, `floorf` for the `float` versions of the math functions.

## Literals and suffixes

| Literal | Type |
|---|---|
| `42` | `int` (or the first of `long`, `long long` that fits) |
| `42u`, `42U` | `unsigned int` |
| `42L`, `42UL`, `42LL`, `42ULL` | `long`, `unsigned long`, `long long`, `unsigned long long` |
| `0x2A` | hexadecimal |
| `052` | **octal**: a leading zero means base 8, so `010 == 8` |
| `0b101010` | binary: a gcc extension, standard only in C23 |
| `3.0`, `3.`, `1e3` | `double` |
| `3.0f` | `float` |
| `'A'`, `'\n'`, `'\0'`, `'\x41'` | `int` |

There are no digit separators like C#'s `1_000_000` (C23 adds `1'000'000`).

## Integer promotion

Arithmetic never happens in a type narrower than `int`. Before any arithmetic, `char`, `short`, `uint8_t`, `uint16_t` and `_Bool` values are **promoted** to `int`. So two `uint8_t` values add up as `int`s:

```c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    uint8_t a = 200, b = 100;
    int sum = a + b;            // 300: computed as int
    uint8_t wrapped = a + b;    // 44: 300 converted back to 8 bits (300 - 256)
    printf("%d %d\n", sum, wrapped);
    uint8_t x = 0xF0;
    printf("%d\n", ~x);         // -241, not 15: ~ applied to the int 0x000000F0
    printf("%d\n", (uint8_t)~x);  // 15
    return 0;
}
```

C# does the same promotion (which is why `byte + byte` is an `int` there and needs a cast back), but C# refuses the implicit narrowing; C silently truncates.

## The usual arithmetic conversions

When a binary operator gets two different types, C converts both to a common type:

1. If either is floating, convert to the widest floating type involved (`long double` > `double` > `float`).
2. Otherwise promote both (see above), then if they still differ, the one with lower *rank* (roughly: size) converts to the other's type...
3. ...**except** that if the unsigned one has rank greater or equal, the signed one converts to **unsigned**. If the signed type is bigger and can hold every value of the unsigned one, the unsigned converts to signed.

Rule 3 is the trap. Mix an `int` and an `unsigned int` and the `int` becomes unsigned, so `-1` turns into `4294967295`:

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    int i = -1;
    unsigned u = 1;
    printf("%d\n", i < u);           // 0: -1 became 4294967295
    printf("%d\n", i < (int)u);      // 1
    printf("%d\n", -1L < 1u);        // 1: long can hold every unsigned int, so 1u -> long

    const char *s = "hi";
    if (strlen(s) - 3 > 0)           // size_t arithmetic: 2 - 3 wraps to 18446744073709551615
        puts("oops: unsigned subtraction never goes negative");
    if ((long)strlen(s) - 3 < 0)
        puts("correct");
    return 0;
}
```

`-Wall -Wextra` turns on `-Wsign-compare`, which warns about the comparison case. Read those warnings. Two habits help: use signed types (`int`, `long`, `ptrdiff_t`) for anything you subtract or count down, and compare sizes as `a < b` rather than `a - b < 0`.

## Overflow: unsigned wraps, signed is undefined

Unsigned arithmetic is **defined** to wrap modulo 2^N: `UINT_MAX + 1u == 0` and `0u - 1 == UINT_MAX`, always. That makes unsigned types right for hashes, checksums and bit twiddling.

Signed overflow is **undefined behavior**. Not "it wraps", not "it throws": the compiler is allowed to assume it never happens, and optimizes on that assumption. With `-O2`, gcc compiles this function to `return 1;`:

```c
int always_bigger(int x) {
    return x + 1 > x;   // "can't overflow, so always true"
}
```

C# wraps silently by default (and throws inside `checked`). In C you must prevent overflow *before* it happens, by checking against the limits:

```c
#include <stdio.h>
#include <limits.h>

int main(void) {
    int gold = INT_MAX, reward = 1;
    if (reward > 0 && gold > INT_MAX - reward)
        puts("would overflow");          // clamp, refuse, or use a wider type
    else
        printf("%d\n", gold + reward);
    printf("%d %d\n", INT_MIN, INT_MAX);
    printf("%u %ld\n", UINT_MAX, LONG_MAX);
    printf("%d %d %d\n", CHAR_BIT, SCHAR_MIN, UCHAR_MAX);
    return 0;
}
```

`<limits.h>` has `CHAR_BIT` (8), `SCHAR_MIN/MAX`, `UCHAR_MAX`, `CHAR_MIN/MAX`, `SHRT_MIN/MAX`, `INT_MIN/MAX`, `UINT_MAX`, `LONG_MIN/MAX`, `ULONG_MAX`, `LLONG_MIN/MAX`, `ULLONG_MAX`. `<float.h>` has `DBL_MAX`, `DBL_EPSILON` and friends. gcc also offers `__builtin_add_overflow(a, b, &result)`, which does the check for you.

Games hit this more than you would think: a score or gold counter that a player farms for weeks, damage multiplied by a stack of buffs, an idle game's numbers. Decide for each counter what happens at the limit (clamp, use `int64_t`, or refuse the action) instead of finding out from a negative gold total.

A few more things that are undefined: `INT_MIN / -1`, `INT_MIN % -1`, `-INT_MIN`, any integer division by zero, shifting by a negative amount or by the type's width or more, and converting a `double` to an integer type that cannot hold it.

## Conversions on assignment and casts

Assignment, argument passing and `return` silently convert to the target type:

| From | To | Result |
|---|---|---|
| any integer | wider integer | the same value |
| any integer | unsigned type | value modulo 2^N (well defined) |
| any integer | narrower signed type that can't hold it | implementation-defined (gcc wraps) |
| floating | integer | truncates toward zero; UB if out of range |
| integer | floating | nearest representable value (big `long long`s lose precision) |
| `double` | `float` | rounded |

A cast `(type)expr` performs the same conversion explicitly. It is mostly there to say "I mean it", and to force a type *before* an operation happens:

```c
#include <stdio.h>

int main(void) {
    int total = 7, count = 2;
    printf("%.2f\n", (double)total / count);  // 3.50: total converted first
    printf("%.2f\n", (double)(total / count)); // 3.00: too late
    printf("%d %d\n", (int)2.9, (int)-2.9);   // 2 -2: truncation toward zero
    printf("%u\n", (unsigned)-1);             // 4294967295
    printf("%d\n", (signed char)200);         // -56 on gcc
    return 0;
}
```

There is no `Convert.ToInt32`, no `Math.Round` behind the scenes, no exception. If you want rounding, use `round`, `floor`, `ceil` or `lround` from `<math.h>`.

> **Performance:** each int-to-float or float-to-int conversion is a separate CPU instruction with a few cycles of latency, and `floor` or `lround` may be library calls. One conversion is nothing; a conversion on every element of an inner loop is a cost you chose by mixing types. Keep a hot loop in one type (all `float` or all `int`), convert once at the edges (when loading data, when writing pixels), and prefer `(int)x` when you know `x >= 0`, since truncation is then the same as `floor`.

## const

`const` makes an object read-only through that name. Writing to it is a compile error:

```c
#include <stdio.h>

int main(void) {
    const int max_hp = 100;
    // max_hp = 200;        // error: assignment of read-only variable
    const double crit_multiplier = 1.5;
    printf("%d %.1f\n", max_hp, max_hp * crit_multiplier);
    return 0;
}
```

Unlike C#'s `const`, a C `const` variable is **not** a compile-time constant. Prior to C23 it cannot be a `case` label, and `int arr[max_hp];` makes a variable-length array rather than a normal one. For true named constants, C programmers use `#define MAX_HP 100` or an `enum { MAX_HP = 100 };`. `const` really earns its keep with pointers, in the pointers chapter.

## Summary of the traps

- Sizes vary by platform; use `<stdint.h>` when they matter and `sizeof` instead of hard-coded numbers.
- Everything narrower than `int` becomes `int` before arithmetic.
- Signed meets unsigned of the same size: signed loses. `-1 < 0u` is false.
- `size_t` arithmetic never goes negative.
- Unsigned overflow wraps; signed overflow is UB. Check before you add.
- Integer division truncates; `int / int` is never a fraction no matter where you store it.
- A leading `0` makes a literal octal.

=== exercise hexval
title: Characters are numbers
--- prompt
Write `int hex_value(char c)` that returns the value of a hexadecimal digit: `'0'`..`'9'` give 0..9, `'a'`..`'f'` and `'A'`..`'F'` give 10..15. Anything else returns `-1`.

Use character arithmetic (`c - '0'`), not a lookup table or a 22-case `switch`.
--- starter
int hex_value(char c) {
    return 0;
}
--- solution
int hex_value(char c) {
    if (c >= '0' && c <= '9') return c - '0';
    if (c >= 'a' && c <= 'f') return c - 'a' + 10;
    if (c >= 'A' && c <= 'F') return c - 'A' + 10;
    return -1;
}
--- harness
int main(void) {
    CHECK_INT(hex_value('0'), 0);
    CHECK_INT(hex_value('7'), 7);
    CHECK_INT(hex_value('9'), 9);
    CHECK_INT(hex_value('a'), 10);
    CHECK_INT(hex_value('c'), 12);
    CHECK_INT(hex_value('f'), 15);
    CHECK_INT(hex_value('A'), 10);
    CHECK_INT(hex_value('F'), 15);
    CHECK_INT(hex_value('g'), -1);
    CHECK_INT(hex_value('G'), -1);
    CHECK_INT(hex_value('/'), -1);
    CHECK_INT(hex_value(':'), -1);
    CHECK_INT(hex_value('@'), -1);
    CHECK_INT(hex_value('`'), -1);
    CHECK_INT(hex_value(' '), -1);

--- hint
`'0'` through `'9'` are consecutive codes (48..57), so `c - '0'` is the digit's value. Letters are consecutive too.

=== exercise lesssu
title: Comparing signed with unsigned
--- prompt
Write `int less_su(int a, unsigned b)` that returns 1 if `a` is *mathematically* less than `b`, and 0 otherwise.

The starter does the obvious `a < b`, which is wrong: `less_su(-1, 0)` returns 0 because `-1` is converted to `4294967295` first. Fix it without using a wider type like `long long` (pretend you are writing the 64-bit version, where no wider type exists).
--- starter
int less_su(int a, unsigned b) {
    return a < b;
}
--- solution
int less_su(int a, unsigned b) {
    if (a < 0) return 1;
    return (unsigned)a < b;
}
--- harness
#include <limits.h>
int main(void) {
    CHECK_INT(less_su(-1, 0u), 1);
    CHECK_INT(less_su(-1, 1u), 1);
    CHECK_INT(less_su(INT_MIN, 0u), 1);
    CHECK_INT(less_su(INT_MIN, UINT_MAX), 1);
    CHECK_INT(less_su(0, 0u), 0);
    CHECK_INT(less_su(0, 1u), 1);
    CHECK_INT(less_su(3, 4u), 1);
    CHECK_INT(less_su(5, 3u), 0);
    CHECK_INT(less_su(7, 7u), 0);
    CHECK_INT(less_su(INT_MAX, (unsigned)INT_MAX), 0);
    CHECK_INT(less_su(INT_MAX, (unsigned)INT_MAX + 1u), 1);
    CHECK_INT(less_su(INT_MAX, UINT_MAX), 1);
    CHECK_INT(less_su(INT_MAX, 0u), 0);
    return TEST_END();
}
--- hint
A negative `a` is less than every unsigned value. Handle that case first.
--- hint
Once you know `a >= 0`, converting it to `unsigned` cannot change its value, so the comparison is safe.

=== exercise saturate
title: Saturating addition
--- prompt
Saturating arithmetic clamps at the limits instead of overflowing: audio and image code use it everywhere. Write both:

- `uint32_t sat_addu(uint32_t a, uint32_t b)`: `a + b`, or `UINT32_MAX` if the true sum is larger.
- `int32_t sat_add(int32_t a, int32_t b)`: `a + b`, or `INT32_MAX` / `INT32_MIN` if the true sum is above / below the range.

Do it **without** a wider type: no `int64_t`, no `long long`. A signed overflow must never actually happen (the sanitizer is watching).
--- starter
#include <stdint.h>

uint32_t sat_addu(uint32_t a, uint32_t b) {
    return a + b;
}

int32_t sat_add(int32_t a, int32_t b) {
    return a + b;
}
--- solution
#include <stdint.h>

uint32_t sat_addu(uint32_t a, uint32_t b) {
    uint32_t s = a + b;          // wraps, which is defined for unsigned
    return s < a ? UINT32_MAX : s;
}

int32_t sat_add(int32_t a, int32_t b) {
    if (b > 0 && a > INT32_MAX - b) return INT32_MAX;
    if (b < 0 && a < INT32_MIN - b) return INT32_MIN;
    return a + b;
}
--- harness
#include <stdint.h>
int main(void) {
    CHECK_UINT(sat_addu(1, 2), 3);
    CHECK_UINT(sat_addu(0, 0), 0);
    CHECK_UINT(sat_addu(UINT32_MAX, 0), UINT32_MAX);
    CHECK_UINT(sat_addu(0, UINT32_MAX), UINT32_MAX);
    CHECK_UINT(sat_addu(UINT32_MAX, 1), UINT32_MAX);
    CHECK_UINT(sat_addu(UINT32_MAX, UINT32_MAX), UINT32_MAX);
    CHECK_UINT(sat_addu(4000000000u, 294967295u), UINT32_MAX);
    CHECK_UINT(sat_addu(4000000000u, 294967296u), UINT32_MAX);
    CHECK_UINT(sat_addu(4000000000u, 294967294u), 4294967294u);

    CHECK_INT(sat_add(INT32_MAX, INT32_MAX), INT32_MAX);
    CHECK_INT(sat_add(INT32_MAX - 1, 1), INT32_MAX);
    CHECK_INT(sat_add(INT32_MIN, 0), INT32_MIN);
    CHECK_INT(sat_add(INT32_MIN, -1), INT32_MIN);

--- hint
Unsigned: the sum wraps (legally) exactly when the result comes out smaller than either operand.
--- hint

=== exercise damage
title: Damage that never overflows
--- prompt
A first piece of combat code. Write `int apply_damage(int hp, int damage, int armor)` that returns the new hit points:

- Armor is subtracted from the damage. If `damage` is positive, the hit always does **at least 1** point ("chip damage"), however high the armor.
- If `damage` is 0 or negative, nothing happens: return `hp` unchanged.
- Hit points never go below 0.

`hp` is between 0 and `INT_MAX`. `damage` and `armor` can be any `int`: a debuff can make armor negative, and a "kill" effect deals `INT_MAX`. So `damage - armor` and `hp - effective` can both overflow an `int`, and signed overflow is undefined behavior (the sanitizer reports it). Here a wider type is the clean fix: do the arithmetic in `long long`, which holds any difference of two `int`s, then clamp and convert back.

The next exercise adds healing to this.
--- starter
int apply_damage(int hp, int damage, int armor) {
    return hp - (damage - armor);
}
--- solution
int apply_damage(int hp, int damage, int armor) {
    if (damage <= 0) return hp;
    long long effective = (long long)damage - armor;
    if (effective < 1) effective = 1;
    long long left = hp - effective;
    return left < 0 ? 0 : (int)left;
}
--- hint
Cast *before* subtracting: `(long long)damage - armor`. `(long long)(damage - armor)` overflows first and converts afterwards.
--- hint
Clamp twice: the effective damage to at least 1, and the result to at least 0.
--- harness

    CHECK_INT(apply_damage(100, -50, 0), 100);
    CHECK_INT(apply_damage(10, 50, 0), 0);
    CHECK_INT(apply_damage(0, 50, 0), 0);
    CHECK_INT(apply_damage(100, 10, -15), 75);
    CHECK_INT(apply_damage(INT_MAX, INT_MAX, INT_MIN), 0);

=== exercise xpcurve
title: An XP curve
--- prompt
Reaching level `L` takes `50 * L * (L - 1)` total experience: level 1 needs 0, level 2 needs 100, level 3 needs 300, level 4 needs 600 (each level costs 100 more than the last). The level cap is `MAX_LEVEL`, 3,000,000.

Write:

- `int64_t xp_for_level(int level)`: the total XP for `level` (1 to `MAX_LEVEL`). At the cap that is about 4.5e14: far beyond `int`. `50 * level * (level - 1)` is computed in `int` and overflows long before the multiplication result reaches the `int64_t` you return it as. Convert first.
- `int level_for_xp(int64_t xp)`: the highest level whose requirement is `<= xp`, never above `MAX_LEVEL`. `xp` is never negative.

The obvious `level_for_xp` counts up from level 1 until the next level costs too much. The tests call it 200,000 times for players near the cap, which makes that loop about 3e11 steps: far over the time limit. The requirement grows with the level, so you can **binary search** the level range (about 22 steps), or start from the square root and correct by one.

> **Performance:** this is a pattern you will meet constantly in games: a value that is cheap to compute in one direction (level to XP) and that you need in the other (XP to level). Search with a monotonic function, use a closed form, or precompute a table. Never scan.
--- starter
#include <stdint.h>

#define MAX_LEVEL 3000000

int64_t xp_for_level(int level) {
    return 50 * level * (level - 1);
}

int level_for_xp(int64_t xp) {
    int level = 1;
    while (level < MAX_LEVEL && xp_for_level(level + 1) <= xp)
        level++;
    return level;
}
--- solution
#include <stdint.h>

#define MAX_LEVEL 3000000

int64_t xp_for_level(int level) {
    return (int64_t)50 * level * (level - 1);
}

int level_for_xp(int64_t xp) {
    int lo = 1, hi = MAX_LEVEL;            // answer is in [lo, hi]
    while (lo < hi) {
        int mid = lo + (hi - lo + 1) / 2;  // round up so lo = mid always moves
        if (xp_for_level(mid) <= xp) lo = mid;
        else hi = mid - 1;
    }
    return lo;
}
--- hint
`(int64_t)50 * level * (level - 1)`: multiplication is left to right, so once the first operand is 64-bit, every step is.
--- hint
Binary search for the last level that fits: keep `lo` as a level known to fit and `hi` as an upper bound, and pick `mid = lo + (hi - lo + 1) / 2` so the range always shrinks.
--- harness

    CHECK_INT(xp_for_level(4), 600);

    CHECK_INT(xp_for_level(3000000), 449999850000000LL);
    CHECK_INT(level_for_xp(0), 1);
    CHECK_INT(level_for_xp(99), 1);
    CHECK_INT(level_for_xp(100), 2);
    CHECK_INT(level_for_xp(599), 3);
    CHECK_INT(level_for_xp(600), 4);
    CHECK_INT(level_for_xp(449999850000000LL), 3000000);
    CHECK_INT(level_for_xp(449999849999999LL), 2999999);
    CHECK_INT(level_for_xp(INT64_MAX), 3000000);
    // 200,000 players near the cap

    int bad = 0;

=== exercise rgba
title: Packing colors
--- prompt
Pixels and vertex colors are usually stored as four bytes packed into one 32-bit value: a quarter of the memory of four `float`s, which matters when there are millions of them. Write:

- `uint8_t unit_to_byte(float v)`: convert a channel from `0.0..1.0` to `0..255`, rounding to nearest. Values below 0 (and NaN) give 0, values above 1 give 255. `unit_to_byte(0.5f)` is 128.
- `uint32_t pack_rgba(uint8_t r, uint8_t g, uint8_t b, uint8_t a)`: `r` in the lowest byte, then `g`, `b`, and `a` in the highest byte. (On a little-endian CPU that puts the bytes in memory in R, G, B, A order, which is what a GPU's `rgba8` texture format expects.)
- `uint8_t channel(uint32_t color, int i)`: byte `i` (0 = r, 3 = a).

The trap is integer promotion: `a << 24` promotes `a` to a *signed* `int` first, and `255 << 24` does not fit in an `int`. Convert each byte to `uint32_t` before shifting.

> **Performance:** float-to-int conversion is cheap per value but not free, and branches on data (`if (v < 0)`) in a loop over a whole image add up. Convert colors once (when loading, or when a value changes), store them packed, and keep per-pixel loops working on the packed form.
--- starter

    return (uint8_t)(v * 255);
}

    return 0;
}

    return 0;
}
--- solution
#include <stdint.h>

uint8_t unit_to_byte(float v) {
    if (!(v > 0.0f)) return 0;           // also catches NaN: every comparison with NaN is false
    if (v >= 1.0f) return 255;
    return (uint8_t)(v * 255.0f + 0.5f);
}

uint32_t pack_rgba(uint8_t r, uint8_t g, uint8_t b, uint8_t a) {
    return (uint32_t)r | (uint32_t)g << 8 | (uint32_t)b << 16 | (uint32_t)a << 24;
}

uint8_t channel(uint32_t color, int i) {
    return (uint8_t)(color >> (8 * i));
}
--- hint
`if (!(v > 0.0f))` is true for negatives, zero and NaN, because every comparison involving NaN is false.
--- hint
`(uint32_t)a << 24`: the cast binds tighter than the shift, so the shift happens in 32-bit unsigned arithmetic. To extract a byte, shift right and let the conversion to `uint8_t` keep the low 8 bits.
--- harness
