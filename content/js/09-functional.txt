## Functions as the unit of reuse

You know LINQ and delegates, and chapter 01 covered closures. This chapter is about the techniques that grow out of treating functions as values: building behavior by wrapping and combining functions instead of subclassing. Procedural graphics is full of them. A procedural texture *is* a function from coordinates to a colour, and complex textures are built by composing small ones (noise, then warp, then contrast, then a colour ramp). Editors for those textures use reducers for undoable state, debounce regeneration while you drag a slider, and memoize expensive lookups.

It also covers where functional style costs too much. Functional code favours allocating new values; per-pixel and per-frame code favours reusing memory. Knowing both, and where the boundary is, is the actual skill.

## Pure functions and immutability

A pure function's result depends only on its arguments, and it changes nothing outside itself. Pure functions are trivially testable, safe to memoize, safe to run in parallel (in workers, or as a GPU shader, which is a pure function by construction), and deterministic: same seed and parameters in, same texture out.

```js
// Impure: mutates shared state that other code also reads.
const settings = { octaves: 4 };
function addOctave() { settings.octaves++; }

// Pure: returns a new preset and leaves the old one alone.
function setParam(preset, key, value) {
  if (preset.params[key] === value) return preset;            // unchanged: return the same object
  return { ...preset, params: { ...preset.params, [key]: value } };
}
const p0 = { name: 'marble', params: { scale: 4, octaves: 5 }, palette: ['#fff', '#888', '#222'] };
const p1 = setParam(p0, 'scale', 8);
console.log(p0.params, p1.params);
console.log(p0.palette === p1.palette, setParam(p1, 'scale', 8) === p1);
```

Copying only along the path you change and sharing everything else is **structural sharing**. It makes "did anything change?" a cheap `===` check, which is what React, Redux and undo systems rely on, and it lets an editor cache the generated texture until its preset object actually changes.

`Object.freeze` makes an object's own properties read-only. It is **shallow**, and writes to a frozen object fail *silently* in sloppy mode and throw in strict mode. Code on this site runs in sloppy mode unless it starts with `'use strict'` (classes and modules are always strict):

```js
'use strict';
const preset = Object.freeze({ seed: 3, colors: { low: '#203040' } });
try { preset.seed = 99; } catch (e) { console.log(e.constructor.name, e.message); }
preset.colors.low = '#000000';            // nested objects are not frozen
console.log(preset);
const deepFreeze = o => { Object.values(o).forEach(v => typeof v === 'object' && v && deepFreeze(v)); return Object.freeze(o); };
console.log(Object.isFrozen(deepFreeze({ a: { b: 1 } }).a));
```

> **Performance:** immutable updates allocate. `vertices = vertices.map(v => ({ ...v, y: v.y + offset }))` creates an object per vertex, and doing it every frame (or every pixel with `{ r, g, b }` objects) keeps the garbage collector busy until it pauses and drops a frame. That is a bad habit in hot code: mutate typed arrays in place (chapter 10). Use immutability where changes are rare and history matters: presets, editor state, scene descriptions, undo stacks, snapshots.

## Composition and pipe

`compose(f, g)(x)` is `f(g(x))` (right to left, the mathematical order). `pipe(f, g)(x)` is `g(f(x))` (left to right, reading order), which most people find clearer. A tone-mapping chain for a grayscale value is a natural pipeline:

```js
const pipe = (...fns) => x => fns.reduce((acc, f) => f(acc), x);
const compose = (...fns) => x => fns.reduceRight((acc, f) => f(acc), x);

const clamp01 = v => Math.min(1, Math.max(0, v));
const contrast = k => v => (v - 0.5) * k + 0.5;
const gamma = g => v => v ** (1 / g);
const posterize = levels => v => Math.round(v * (levels - 1)) / (levels - 1);

const tone = pipe(contrast(1.5), clamp01, gamma(2.2), posterize(5));
console.log([0, 0.25, 0.5, 0.75, 1].map(tone));
console.log(compose(x => x + 1, x => x * 2)(3), pipe(x => x + 1, x => x * 2)(3));
```

The same idea one level up: a **texture function** maps `(u, v)` in [0, 1] to a value, and combinators build new texture functions from old ones without touching any pixels:

```js
const checker = n => (u, v) => (Math.floor(u * n) + Math.floor(v * n)) & 1;
const circle = r => (u, v) => Math.hypot(u - 0.5, v - 0.5) < r ? 1 : 0;
const scale = (s, f) => (u, v) => f((u * s) % 1, (v * s) % 1);
const mix = (a, b, t) => (u, v) => a(u, v) * (1 - t) + b(u, v) * t;
const invert = f => (u, v) => 1 - f(u, v);

const tex = mix(checker(4), invert(scale(2, circle(0.3))), 0.5);
const W = 24, H = 12, ramp = ' .:-=+*#';
for (let y = 0; y < H; y++) {
  let row = '';
  for (let x = 0; x < W; x++) row += ramp[Math.round(tex((x + 0.5) / W, (y + 0.5) / H) * (ramp.length - 1))];
  console.log(row);
}
```

> **Performance:** a composed texture is a tree of closures, and evaluating it costs several function calls per pixel. That is fine for previews and for small textures, and modern JITs inline a lot of it, but it is not free: a 2048 by 2048 texture is four million evaluations of the whole tree. Two standard remedies: compile the tree into a single function (the projects chapter does this for formula strings) or bake intermediate layers into `Float32Array`s once and combine those. Never allocate inside a texture function (no `[r, g, b]` arrays per pixel); write into preallocated output instead.

## Currying and partial application

**Partial application** fixes some arguments and returns a function of the rest (`bind` does it, and so does any closure). **Currying** turns an n-argument function into a chain of one-argument functions. A practical `curry` collects arguments until it has `fn.length` of them:

```js
function curry(fn) {
  return function curried(...args) {
    return args.length >= fn.length
      ? fn.apply(this, args)
      : (...more) => curried.apply(this, [...args, ...more]);
  };
}
const dist2 = curry((x1, y1, x2, y2) => (x2 - x1) ** 2 + (y2 - y1) ** 2);
const fromOrigin = dist2(0, 0);
console.log(fromOrigin(3, 4), dist2(1)(1)(4, 5), dist2(1, 1, 4, 5));

const log = (level, system, msg) => `[${level}] ${system}: ${msg}`;
const warnShader = log.bind(null, 'WARN', 'shader');
console.log(warnShader('uniform uTime is unused'));
console.log(((a, b = 2, ...c) => 0).length, (function (a, b) {}).length);
```

Note `fn.length` counts parameters before the first default or rest parameter, so `curry` does not work for those. Currying is less common in everyday JavaScript than in Haskell or F#; closures that fix a few arguments (`contrast(1.5)` above) are the everyday form.

## Memoization

A memoized function caches results by argument. It only makes sense for **pure** functions, and the key choice is where the bugs hide:

```js
function memoize(fn) {
  const cache = new Map();
  return arg => {
    if (cache.has(arg)) return cache.get(arg);
    const v = fn(arg);
    cache.set(arg, v);
    return v;
  };
}
let calls = 0;
const fib = memoize(n => { calls++; return n < 2 ? n : fib(n - 1) + fib(n - 2); });
console.log(fib(70), calls);
```

The memoized `fib` calls itself through the cache, so it is linear instead of exponential. For several arguments, the tempting key `args.join(',')` or `JSON.stringify(args)` conflates `1` with `'1'` (`join`), loses object identity (two different meshes with equal fields share an entry), costs a string allocation per call, and throws on cycles and bigints. The robust structure is a **trie of Maps**, one level per argument, keyed by the arguments themselves (Maps use SameValueZero, so `NaN` works and objects are compared by identity). Use a `WeakMap` level for object keys if the cache must not keep them alive.

> **Performance:** memoization trades memory for time, and both sides have costs. A `Map` lookup is a hash plus a probe: cheaper than generating a noise tile or triangulating a glyph, *far more expensive* than `a * b + c`. Memoizing a cheap per-pixel function makes it slower, and a cache keyed on float coordinates almost never hits. An unbounded cache is a memory leak with a nice name: measure first, cap the size (an LRU cache, chapter 12), or prefer a **precomputed table** indexed by an integer (a gradient table, a gamma lookup table of 256 entries), which is the procedural-generation version of memoization with no hashing at all.

## Debounce and throttle

Both limit how often a function runs:

- **debounce**: run once, after calls *stop* for `ms` milliseconds (regenerate a 2048 by 2048 texture after the user stops dragging the "scale" slider, save settings, re-layout on resize).
- **throttle**: run at most once per `ms`, at a steady rate while calls continue (a cheap low-resolution preview while the slider moves, scroll handlers, network updates).

```js
function debounce(fn, ms) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);
  };
}
function throttle(fn, ms) {
  let last = -Infinity;
  return function (...args) {
    const now = performance.now();
    if (now - last >= ms) { last = now; return fn.apply(this, args); }
  };
}

const sleep = ms => new Promise(r => setTimeout(r, ms));
const regenerate = debounce(scale => console.log('full-res texture at scale', scale), 40);
for (const s of [2, 3, 4]) { regenerate(s); await sleep(5); }
await sleep(80);

const preview = throttle(s => console.log('preview at scale', s), 30);
for (let i = 0; i < 10; i++) { preview(i); await sleep(10); }
```

The throttle above is *leading-edge only*: the last call in a burst may be dropped, so the preview may not match the final slider position. A full implementation also schedules a *trailing* call with the latest arguments; you will write one in the exercises.

Inside a render loop, do not use timers at all. Timers fire between frames at unpredictable moments and keep running while the app is paused. Animation advances by the frame's `dt` (seconds since the last frame), and anything periodic is a countdown decremented by `dt`. Debounce and throttle are for the edges: UI, regeneration requests, saving, networking.

## once and function decorators

A decorator takes a function and returns a wrapped function with extra behavior. The wrapper must pass through `this` and all arguments, so write it with `function` and `apply`, not an arrow:

```js
function once(fn) {
  let done = false, result;
  return function (...args) {
    if (!done) { done = true; result = fn.apply(this, args); }
    return result;
  };
}
function timed(fn, label = fn.name) {
  return function (...args) {
    const t0 = performance.now();
    try { return fn.apply(this, args); }
    finally { const ms = performance.now() - t0; if (ms > 1000) console.log(`${label} took ${ms.toFixed(1)}ms`); }
  };
}
const initGpu = once(() => { console.log('requesting GPU device'); return { ready: true }; });
console.log(initGpu(), initGpu() === initGpu());

const mesh = { triangles: 12, subdivide: timed(function (k) { return this.triangles *= 4 ** k; }) };
console.log(mesh.subdivide(2), mesh.triangles);
```

Decorators compose like any other function: `const build = once(timed(buildAtlas))`. The TC39 `@decorator` syntax for classes is standardized but not yet shipped in browsers, so you only see it with a build step (TypeScript, Babel); underneath it is exactly this pattern.

## Recursion, stack depth and trampolines

V8 does not implement proper tail calls, so every recursive call uses a stack frame, and the stack holds roughly ten thousand frames. A recursive flood fill on a 200 by 200 grid, a recursive walk over a deep scene graph, or a recursive L-system interpreter at high generation counts throws `RangeError: Maximum call stack size exceeded`.

```js
const depth = n => n === 0 ? 0 : 1 + depth(n - 1);
try { depth(1e6); } catch (e) { console.log(e.name, e.message); }

// Trampoline: return a thunk instead of recursing; a loop calls thunks until a value comes out.
const trampoline = fn => (...args) => {
  let r = fn(...args);
  while (typeof r === 'function') r = r();
  return r;
};
const sumTo = trampoline(function go(n, acc = 0) {
  return n === 0 ? acc : () => go(n - 1, acc + n);
});
console.log(sumTo(1e6));
```

A trampoline keeps the recursive shape of the code. Usually the clearer fix is a loop with an explicit stack (an array you `push` and `pop`), which is also how you make depth-first searches over grids and graphs safe and fast.

> **Performance:** a trampoline allocates one closure per step, so it is a correctness fix, not a speed fix. An explicit stack of plain integers (`stack.push(x, y)`, or `y * width + x` packed into one number) allocates almost nothing.

## Reducers

A reducer is a pure function `(state, action) => newState`. All changes go through one place, actions are plain data (so they can be logged, sent over the network, or replayed), undo is "keep the old states", and the current state is just `actions.reduce(reducer, initial)`. A layer stack in a texture editor:

```js
function layers(state, action) {
  switch (action.type) {
    case 'add':
      return [...state, { id: action.id, kind: action.kind, opacity: 1 }];
    case 'opacity': {
      const i = state.findIndex(l => l.id === action.id);
      if (i < 0 || state[i].opacity === action.value) return state;
      return state.map((l, j) => (j === i ? { ...l, opacity: action.value } : l));
    }
    case 'remove':
      return state.some(l => l.id === action.id) ? state.filter(l => l.id !== action.id) : state;
    default:
      return state;
  }
}
const history = [[]];
for (const a of [
  { type: 'add', id: 1, kind: 'noise' },
  { type: 'add', id: 2, kind: 'gradient' },
  { type: 'opacity', id: 2, value: 0.5 },
  { type: 'opacity', id: 2, value: 0.5 },
  { type: 'remove', id: 1 },
]) history.push(layers(history.at(-1), a));
console.log(history.at(-1), history[3] === history[4], history[2][0] === history[3][0]);
```

Returning the same `state` object for an action that changes nothing matters: it lets every consumer (the renderer, the undo stack) skip work with a single `===`.

## State machines

Character controllers, camera modes, animation blending, tool modes in an editor and network connections are all state machines: a finite set of states, and events that move between them. Writing the transitions as **data** instead of nested `if`s makes them inspectable, testable and easy to draw:

```js
const CAMERA = {
  orbit: { dragMiddle: 'pan', wheel: 'zoom', pressF: 'fly' },
  pan:   { release: 'orbit' },
  zoom:  { idle: 'orbit' },
  fly:   { pressF: 'orbit', escape: 'orbit' },
};
function transition(state, event) {
  return CAMERA[state][event] ?? state;      // unknown events are ignored
}
let s = 'orbit';
for (const ev of ['wheel', 'idle', 'pressF', 'wheel', 'escape', 'dragMiddle', 'release']) {
  const next = transition(s, ev);
  console.log(`${s} --${ev}--> ${next}`);
  s = next;
}
```

Each state can also carry per-state behavior (`enter`, `update(dt)`, `exit` functions), which turns the table into a full controller without a single subclass.

title: pipe and curry
--- prompt
Write three functions:

- `pipe(...fns)` returns a function that passes its argument through each function left to right. `pipe()` with no functions is the identity. The first function may take several arguments: `pipe(Math.max, x => x * 2)(1, 5, 3)` is `10`.
- `compose(...fns)` is the same but right to left; the *last* function may take several arguments.
- `curry(fn, arity = fn.length)` returns a curried version that accepts arguments in any grouping (`f(1)(2)(3)`, `f(1, 2)(3)`, `f(1)(2, 3)`, `f(1, 2, 3)`). Calling with no arguments does not advance (`f()(1)()(2, 3)` still works). Extra arguments in the final call are passed through. The curried function must keep `this` (from the call that completes the arguments), and partial applications must be independent: `const a = f(1); a(2)(3); a(5)(6)` must not interfere.
--- starter
function pipe(...fns) {
  return x => x;
}

function compose(...fns) {
  return x => x;
}

function curry(fn, arity = fn.length) {
  return fn;
}
--- solution
function pipe(...fns) {
  if (!fns.length) return x => x;
  const [first, ...rest] = fns;
  return function (...args) {
    return rest.reduce((acc, f) => f.call(this, acc), first.apply(this, args));
  };
}

function compose(...fns) {
  return pipe(...fns.reverse());
}

function curry(fn, arity = fn.length) {
  return function curried(...args) {
    if (args.length >= arity) return fn.apply(this, args);
    return function (...more) {
      return curried.apply(this, [...args, ...more]);
    };
  };
}
--- hint
For `pipe`, call the first function with all the arguments, then `reduce` over the rest with the single running value.
--- hint
`curry`'s inner function closes over the arguments collected so far and never mutates them; it creates a new array `[...args, ...more]` per call, which is what keeps partial applications independent.
--- harness

  eq(compose(x => x + 1, x => x * 2)(3), 7);

  eq(compose(x => x * 2, Math.max)(1, 5, 3), 10, 'last function takes several args');
  eq(compose()('a'), 'a');

=== exercise memo
title: A correct memoize
--- prompt
Write `memoize(fn)` that caches results for **any number of arguments** using a trie of `Map`s (one level per argument, then a terminal entry), so that:

- arguments are compared like Map keys (SameValueZero): `1` and `'1'` are different, `NaN` matches `NaN`, objects match only by identity;
- calls with different numbers of arguments do not collide (`f(1)` vs `f(1, undefined)` vs `f()`);
- `this` is passed through to `fn` (it is not part of the key);
- exceptions are not cached (the next call tries again);
- the returned function has a `clear()` method that empties the cache and a `cacheSize()` method that returns the number of cached results.

One subtlety: a trie node can need both "the result for exactly these arguments" and "deeper levels for longer argument lists". Store the result under a key that no argument can equal, such as a `Symbol()` created inside `memoize` (chapter 11), or keep separate maps for children and results.
--- starter
function memoize(fn) {
  const cache = new Map();
  const m = function (...args) {
    const key = args.join(',');
    if (!cache.has(key)) cache.set(key, fn.apply(this, args));
    return cache.get(key);
  };
  m.clear = () => cache.clear();
  m.cacheSize = () => cache.size;
  return m;
}
--- solution
function memoize(fn) {
  const RESULT = Symbol('result');
  let root = new Map(), count = 0;
  const m = function (...args) {
    let node = root;
    for (const a of args) {
      let next = node.get(a);
      if (!next) { next = new Map(); node.set(a, next); }
      node = next;
    }
    if (node.has(RESULT)) return node.get(RESULT);
    const v = fn.apply(this, args);
    node.set(RESULT, v);
    count++;
    return v;
  };
  m.clear = () => { root = new Map(); count = 0; };
  m.cacheSize = () => count;
  return m;
}
--- hint
Walk one `Map` per argument, creating levels as needed. The node you end on represents exactly this argument list; store the result there under a `Symbol` key, which can never collide with an argument value.
--- hint
If `fn` throws, the `node.set(RESULT, ...)` line is never reached, so nothing is cached. Keep a counter for `cacheSize`.
--- harness
{
  let calls = 0;
  const f = memoize((...args) => { calls++; return args.length + ':' + args.map(String).join('|'); });
  eq(f(1, 2), '2:1|2'); eq(f(1, 2), '2:1|2'); eq(calls, 1, 'cached');
  eq(f('1', 2), '2:1|2'); eq(calls, 2, "'1' differs from 1");
  eq(f('1,2'), '1:1,2'); eq(calls, 3, 'no join collisions');
  f(); f(); eq(calls, 4, 'zero args cached');
  f(1); f(1, undefined); f(1, undefined); eq(calls, 6, 'f(1) and f(1, undefined) differ');
  f(NaN); f(NaN); eq(calls, 7, 'NaN matches NaN');
  const e1 = { id: 1 }, e2 = { id: 1 };
  f(e1); f(e1); f(e2); eq(calls, 9, 'objects by identity');
  eq(f.cacheSize(), 9);
  f.clear();
  eq(f.cacheSize(), 0);
  f(1, 2); eq(calls, 10, 'recomputed after clear');

  const obj = { k: 5, get: memoize(function (x) { return this.k * x; }) };
  eq(obj.get(2), 10, 'this passed through');

  let n = 0;
  const flaky = memoize(x => { if (n++ === 0) throw new Error('first time fails'); return x * 2; });
  throws(() => flaky(4), 'first call throws');
  eq(flaky(4), 8, 'exception not cached');
  eq(flaky.cacheSize(), 1);

  const undef = memoize(() => { n++; return undefined; });
  const before = n; undef(); undef();
  eq(n - before, 1, 'undefined results are cached too');

  let pc = 0;
  const pathCost = memoize((a, b) => { pc++; return Math.abs(a.x - b.x) + Math.abs(a.y - b.y); });
  const tiles = Array.from({ length: 50 }, (_, i) => ({ x: i % 7, y: (i * 3) % 11 }));

}

=== exercise timing
title: debounce and throttle
--- prompt
Write `debounce(fn, ms)` and `throttle(fn, ms)` with these exact behaviors. Both must pass `this` and the arguments through.

**`debounce`** calls `fn` once, `ms` after the *last* call, with the arguments of that last call. The returned function also has:

- `cancel()`: drop any pending call;
- `flush()`: if a call is pending, run it immediately (and cancel the timer); otherwise do nothing.

**`throttle`** calls `fn` **immediately** on the first call (leading edge), then ignores calls until `ms` has passed, except that if any calls arrived during that window, it calls `fn` **once more at the end of the window** with the latest arguments (trailing edge), which starts a new window. So 10 rapid calls in less than `ms` produce exactly 2 invocations: the first and the last.

The tests use real timers with generous margins (windows of 60 to 100 ms).
--- starter
function debounce(fn, ms) {
  const d = (...args) => fn(...args);
  d.cancel = () => {};
  d.flush = () => {};
  return d;
}

function throttle(fn, ms) {
  return (...args) => fn(...args);
}
--- solution
function debounce(fn, ms) {
  let timer = null, pending = null;
  const run = () => {
    const { self, args } = pending;
    pending = null; timer = null;
    fn.apply(self, args);
  };
  const d = function (...args) {
    pending = { self: this, args };
    clearTimeout(timer);
    timer = setTimeout(run, ms);
  };
  d.cancel = () => { clearTimeout(timer); timer = null; pending = null; };
  d.flush = () => { if (pending) { clearTimeout(timer); run(); } };
  return d;
}

function throttle(fn, ms) {
  let timer = null, pending = null;
  const endWindow = () => {
    timer = null;
    if (pending) {
      const { self, args } = pending;
      pending = null;
      fn.apply(self, args);
      timer = setTimeout(endWindow, ms);
    }
  };
  return function (...args) {
    if (timer === null) {
      fn.apply(this, args);
      timer = setTimeout(endWindow, ms);
    } else {
      pending = { self: this, args };
    }
  };
}

    const du = u - 0.5, dv = v - 0.5;

  screen: (a, b) => 1 - (1 - a) * (1 - b),
  add: (a, b) => Math.min(1, a + b),
  difference: (a, b) => Math.abs(a - b),

  if (!Object.hasOwn(BLEND_, mode)) throw new RangeError(`unknown blend mode: ${mode}`);
  const op = BLEND_[mode];

  const out = new Float32Array(width * height);
  for (let y = 0, i = 0; y < height; y++) {
    const v = (y + 0.5) / height;
    for (let x = 0; x < width; x++, i++) out[i] = f((x + 0.5) / width, v);

  return out;

--- solution
function floodFill(grid, x, y, fill) {
  const h = grid.length;
  if (y < 0 || y >= h || x < 0 || x >= grid[y].length) return grid;
  const target = grid[y][x];
  if (target === fill) return grid;
  const g = grid.map(r => r.split(''));
  const stack = [x, y];
  while (stack.length) {
    const cy = stack.pop(), cx = stack.pop();
    if (cy < 0 || cy >= h || cx < 0 || cx >= g[cy].length || g[cy][cx] !== target) continue;
    g[cy][cx] = fill;
    stack.push(cx + 1, cy, cx - 1, cy, cx, cy + 1, cx, cy - 1);
  }
  return g.map(r => r.join(''));
}

--- prompt

State: `{ objects: [{ id, mesh, pos: [x, y, z] }, ...], selected, nextId }`.

| action | effect |
|---|---|
| `{ type: 'add', mesh }` | append `{ id: mesh + nextId, mesh, pos: [0, 0, 0] }`, increment `nextId`, select the new object |
| `{ type: 'move', id, delta: [dx, dy, dz] }` | add `delta` to the object's `pos` (a new array). Missing id or an all-zero delta: no change |
| `{ type: 'remove', id }` | remove the object; if it was selected, `selected` becomes `null`. Missing id: no change |
| `{ type: 'select', id }` | select an existing object, or deselect with `id: null`. Selecting a missing id, or what is already selected: no change |
| anything else | no change |

Never mutate. When nothing changes, return **the same `state` object**. When something changes, share everything you did not change (untouched objects and their `pos` arrays keep their identity).

`undoable(reducer)` returns a reducer over `{ past: [], present, future: [] }`:

- `{ type: 'undo' }` / `{ type: 'redo' }` move between `past`, `present` and `future` (no change when there is nothing to undo/redo);
- any other action runs `reducer(present, action)`. If the result is the same object, return the wrapper state unchanged (so no-op actions do not create undo steps); otherwise push the old present onto `past` and clear `future`.

The harness starts from `{ past: [], present: initial, future: [] }`.
--- starter

    state.nextId++;
  }
  return state;
}

function undoable(reducer) {
  return (state, action) => ({ ...state, present: reducer(state.present, action) });
}
--- solution
function sceneReducer(state, action) {
  const find = id => state.objects.findIndex(o => o.id === id);
  switch (action.type) {
    case 'add': {
      const obj = { id: action.mesh + state.nextId, mesh: action.mesh, pos: [0, 0, 0] };
      return { objects: [...state.objects, obj], selected: obj.id, nextId: state.nextId + 1 };
    }
    case 'move': {
      const i = find(action.id), d = action.delta;
      if (i < 0 || d.every(x => x === 0)) return state;
      const objects = state.objects.map((o, j) => (j === i ? { ...o, pos: o.pos.map((p, k) => p + d[k]) } : o));
      return { ...state, objects };
    }
    case 'remove': {
      if (find(action.id) < 0) return state;
      return {
        ...state,
        objects: state.objects.filter(o => o.id !== action.id),
        selected: state.selected === action.id ? null : state.selected,
      };
    }
    case 'select': {
      if (action.id === state.selected) return state;
      if (action.id !== null && find(action.id) < 0) return state;
      return { ...state, selected: action.id };
    }
    default:
      return state;
  }
}

function undoable(reducer) {
  return (state, action) => {
    const { past, present, future } = state;
    if (action.type === 'undo') {
      if (!past.length) return state;
      return { past: past.slice(0, -1), present: past.at(-1), future: [present, ...future] };
    }
    if (action.type === 'redo') {
      if (!future.length) return state;
      return { past: [...past, present], present: future[0], future: future.slice(1) };
    }
    const next = reducer(present, action);
    if (next === present) return state;
    return { past: [...past, present], present: next, future: [] };
  };
}
