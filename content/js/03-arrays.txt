## Arrays are lists (mostly)

A JavaScript array is a growable, zero-indexed list of any values, closer to C#'s `List<object>` than to `T[]`. It's technically an object whose keys are integer strings plus a magic `length`, but engines store it as a real contiguous buffer as long as you treat it like one.

```js
const layers = ['albedo', 'normal'];
layers.push('roughness');            // add at end (amortized O(1))
const last = layers.pop();        // remove from end, O(1)
layers.unshift('height');          // add at front: O(n), shifts everything
const first = layers.shift();     // remove from front: O(n)
console.log(layers, last, first, layers.length, layers.at(-1), layers[99]);
console.log(layers.indexOf('normal'), layers.includes('metal'), layers.join(' + '));

const removed = layers.splice(0, 1, 'ao', 'metal');   // at index 0, remove 1, insert 2
console.log(removed, layers, layers.slice(1), layers.concat(['emissive']));
```

`push`/`pop` at the end are cheap; `shift`/`unshift`/`splice` in the middle move every later element. Reading out of bounds returns `undefined` rather than throwing.

> **Performance:** a queue built on `push` + `shift` is O(n) per dequeue. Fine for 10 items, quadratic for the queue of a flood fill or breadth-first search that visits a million pixels. Use a read index (`queue[head++]`) or a ring buffer, ideally over a preallocated `Int32Array`. Similarly `arr.includes(x)` is a linear scan: for "is this pixel visited?" checks inside a loop, use a flat `Uint8Array` of flags indexed by `y * width + x` (or a `Set` when the domain is unbounded).

## The iteration methods

These are LINQ, eagerly evaluated. Each callback gets `(element, index, array)`.

| Method | Returns | LINQ |
|---|---|---|
| `map(f)` | new array of `f(x)` | `Select` |
| `filter(f)` | new array of elements where `f(x)` is truthy | `Where` |
| `reduce(f, init)` | accumulated value | `Aggregate` |
| `find(f)` / `findLast(f)` | first / last matching element or `undefined` | `FirstOrDefault` / `LastOrDefault` |
| `findIndex(f)` / `findLastIndex(f)` | index or `-1` | |
| `some(f)` / `every(f)` | boolean, short-circuits | `Any` / `All` |
| `flatMap(f)` | map then flatten one level | `SelectMany` |
| `flat(depth = 1)` | flattened copy | |
| `includes(x)` | boolean (SameValueZero, finds `NaN`) | `Contains` |
| `forEach(f)` | `undefined` (can't `break`) | |

```js
const meshes = [
  { name: 'rock', tris: 120, visible: true, tags: ['static'] },
  { name: 'tree', tris: 3400, visible: true, tags: ['foliage', 'wind'] },
  { name: 'grass', tris: 800, visible: false, tags: ['foliage', 'wind'] },
  { name: 'cliff', tris: 9000, visible: true, tags: ['static', 'lod'] },
];
const shown = meshes.filter(m => m.visible);
console.log(shown.map(m => m.name));
console.log(shown.reduce((sum, m) => sum + m.tris, 0));
console.log(meshes.find(m => m.tris > 1000)?.name, meshes.findIndex(m => !m.visible));
console.log(meshes.some(m => m.tags.includes('lod')), meshes.every(m => m.tris > 0));
console.log(meshes.flatMap(m => m.tags), [[1, [2]], [3]].flat(Infinity));
```

### reduce, properly

Always pass the initial value. Without it, `reduce` uses the first element as the accumulator and **throws on an empty array**. With it, the accumulator can be any type: a number, an object, a `Map`.

```js
const biomes = ['sea', 'sand', 'sea', 'sea', 'rock', 'sand'];   // one per sampled pixel
const counts = biomes.reduce((acc, b) => {
  acc[b] = (acc[b] ?? 0) + 1;
  return acc;
}, {});
console.log(counts);

const lights = [{ name: 'fill', lumens: 300 }, { name: 'key', lumens: 1200 }, { name: 'rim', lumens: 600 }];
const brightest = lights.reduce((best, l) => (l.lumens > best.lumens ? l : best));
console.log(brightest.name);
try { [].reduce((a, b) => a + b); } catch (e) { console.log(e.name); }
```

Don't write `reduce((acc, x) => ({ ...acc, [x.id]: x }), {})`: spreading the accumulator copies it every step, making an O(n) job O(n²). Mutate the accumulator you own, or use `Object.fromEntries`/`new Map(...)`.

### Chains versus loops

```js
const heights = [0.2, -0.4, 0.9, -0.1, 0.5];      // terrain samples; below 0 is under water
// readable: three passes, two temporary arrays
const landEnergy = heights.filter(h => h > 0).map(h => h * h).reduce((a, b) => a + b, 0);

// one pass, no allocation
let energy = 0;
for (let i = 0; i < heights.length; i++) { const h = heights[i]; if (h > 0) energy += h * h; }
console.log(landEnergy.toFixed(2), energy.toFixed(2));
```

> **Performance:** each `map`/`filter`/`slice`/`concat`/spread allocates a new array. In code that runs once (loading a scene, building a UI) the chain is the right choice: clearer, and the cost is invisible. In per-frame or per-pixel code over millions of elements, those temporaries become garbage-collector pauses that show up as stutter, and memory traffic that dwarfs the actual math. Use indexed `for` loops (or `for...of`) in hot paths, reuse arrays (`arr.length = 0` empties one in place), and keep the functional style for everything else. Measure with `performance.now()` before rewriting anything.

## Sorting: the classic trap

`sort()` **mutates** the array and, without a comparator, **sorts as strings**. So numbers sort lexicographically:

```js
const scores = [100, 25, 3, 1000, 42];
console.log([...scores].sort());                  // strings!
console.log([...scores].sort((a, b) => a - b));   // numeric ascending
console.log([...scores].sort((a, b) => b - a));   // descending
```

The comparator returns negative (a first), positive (b first), or zero. Rules:

- For numbers, `a - b`. Don't return a boolean (`a > b`): it's never negative, so the sort is wrong in engine-dependent ways.
- For strings, `a.localeCompare(b)` (locale-aware) or `a < b ? -1 : a > b ? 1 : 0` (code-unit order, faster and deterministic).
- Sort is **stable** (guaranteed since ES2019): equal elements keep their order, so you can sort by a secondary key with `||` chaining.

```js
const board = [
  { name: 'cy', score: 50, time: 30 },
  { name: 'ada', score: 80, time: 45 },
  { name: 'bob', score: 50, time: 20 },
  { name: 'dee', score: 80, time: 45 },
];
const ranked = board.toSorted((a, b) => b.score - a.score || a.time - b.time || a.name.localeCompare(b.name));
console.log(ranked.map(p => p.name), board[0].name);
```

### Non-mutating versions (ES2023)

`toSorted`, `toReversed`, `toSpliced` and `with(index, value)` return new arrays and leave the original alone. Use them whenever the array isn't yours to mutate (props, shared state); the old idiom was `[...arr].sort()`.

```js
const order = [3, 1, 2];
console.log(order.toSorted(), order.toReversed(), order.with(0, 9), order.toSpliced(1, 1), order);
```

`reverse()`, `sort()`, `splice()`, `fill()`, `copyWithin()`, `push`/`pop`/`shift`/`unshift` mutate. `map`, `filter`, `slice`, `concat`, `flat`, `to*`, `with` don't.

## Creating arrays and ranges

There's no `Enumerable.Range`. `Array.from` takes an iterable or an array-like (`{ length: n }`) plus a mapping function:

```js
const range = (start, end, step = 1) => Array.from({ length: Math.max(0, Math.ceil((end - start) / step)) }, (_, i) => start + i * step);
console.log(range(0, 5), range(10, 0, -3), range(0, 1, 0.25));

const grid = Array.from({ length: 3 }, () => Array(4).fill('.'));   // 3 rows of 4
grid[1][2] = '#';
console.log(grid.map(row => row.join('')));

const shared = Array(3).fill([]);   // trap: ONE array, three references
shared[0].push('x');
console.log(shared);
console.log(Array.from('abc'), Array.from(new Set([1, 1, 2])), Array.of(7), Array(7).length);
```

`fill(obj)` puts the *same* object in every slot. For a grid, give `Array.from` a function so each row is new.

> **Performance:** for images, height fields and grids, prefer one flat array of `width * height` cells indexed by `y * width + x` over an array of row arrays: one allocation, contiguous memory, one bounds check, and trivially copyable. With a typed array (`new Uint8Array(w * h)`, or `Float32Array` for heights) it's also compact: one byte or four per cell instead of an 8-byte reference to a boxed value, and it's the layout canvas `ImageData` and GPU textures use.

## Holes and sparse arrays

`Array(5)`, `[1, , 3]`, `delete arr[i]` or writing `arr[100]` on a short array create **holes**: indexes that don't exist (different from holding `undefined`). Iteration methods (`forEach`, `map`, `filter`, `reduce`) *skip* holes; `for...of`, spread and `Array.from` treat them as `undefined`.

```js
const holey = [1, , 3];
console.log(holey.length, 1 in holey, holey[1]);
let visits = 0;
holey.forEach(() => visits++);
console.log(visits, [...holey], Array.from(holey, x => x ?? 0));
console.log(Array(3).map(() => 'x').length, Array(3).map(() => 'x')[0], Array.from({ length: 3 }, () => 'x'));
```

> **Performance:** engines track an array's "elements kind": packed small integers, packed doubles, packed anything, and HOLEY variants of each. Transitions only go towards the slower, more general kinds, never back. Creating holes (`delete arr[i]`, `new Array(n)` then filling out of order, writing past the end) or mixing types (putting a string into a number array) slows every later access to that array. Preallocate by pushing in order or with `Array.from`/`fill`, keep arrays homogeneous, and never `delete` from an array; for numeric data use typed arrays.

## Destructuring arrays

```js
const [first, second = 'none', ...others] = ['a'];
console.log(first, second, others);

const [, , third] = [1, 2, 3];               // skip with commas
let px = 1, py = 2;
[px, py] = [py, px];                          // swap
console.log(third, px, py);

const [[x0, y0], [x1, y1]] = [[0, 0], [3, 4]];
console.log(Math.hypot(x1 - x0, y1 - y0));

for (const [i, name] of ['ada', 'bob'].entries()) console.log(i, name);
```

The swap idiom is elegant but allocates a temporary array; in a hot inner loop (sorting, shuffling) use a `const t = a[i]; a[i] = a[j]; a[j] = t;` swap.

## Grouping

`Object.groupBy(items, keyFn)` (ES2024) groups into a null-prototype object of arrays; `Map.groupBy` does the same into a `Map` (use it when keys aren't strings).

```js
const textures = [
  { file: 'bark.png', format: 'rgba8', kb: 512 },
  { file: 'height.exr', format: 'r32f', kb: 4096 },
  { file: 'moss.png', format: 'rgba8', kb: 256 },
  { file: 'normal.png', format: 'rg8', kb: 1024 },
];
const byFormat = Object.groupBy(textures, t => t.format);
console.log(Object.keys(byFormat), byFormat.rgba8.map(t => t.file));
const bySize = Map.groupBy(textures, t => (t.kb >= 1024 ? 'large' : 'small'));
console.log([...bySize.keys()], bySize.get('small').length);
```

## Common transformations

```js
const mats = [
  { id: 7, name: 'bark', shader: 'pbr', samplers: 3 },
  { id: 3, name: 'water', shader: 'refract', samplers: 2 },
  { id: 9, name: 'moss', shader: 'pbr', samplers: 4 },
];
// index by id (build once, then O(1) lookups instead of find() in a loop)
const byId = new Map(mats.map(m => [m.id, m]));
console.log(byId.get(9).name);

// totals per shader
const samplersPerShader = {};
for (const m of mats) samplersPerShader[m.shader] = (samplersPerShader[m.shader] ?? 0) + m.samplers;
console.log(samplersPerShader);

// unique values, preserving order
console.log([...new Set(mats.map(m => m.shader))]);

// zip two arrays: positions with colors
const pos = [0, 1, 2], col = ['red', 'green', 'blue'];
console.log(pos.map((p, i) => [p, col[i]]));

// chunk flat vertex data into [x, y, z] triples
const chunk = (arr, n) => Array.from({ length: Math.ceil(arr.length / n) }, (_, i) => arr.slice(i * n, i * n + n));
console.log(chunk([0, 0, 0, 1, 0, 0, 0, 1, 0], 3));

// partition into [matching, rest] in one pass
const [heavy, light] = mats.reduce((acc, m) => (acc[m.samplers >= 3 ? 0 : 1].push(m), acc), [[], []]);
console.log(heavy.length, light.length);
```

The "index by id once" pattern matters: `ids.map(id => mats.find(m => m.id === id))` is O(n·m) and is one of the most common accidental quadratic loops in JavaScript code.

### Removing items from a particle list

Removing dead particles from the middle of an array with `splice` while iterating is both buggy (indexes shift under you) and O(n) per removal. When order doesn't matter, which is usual for particles, use **swap-remove**: overwrite the dead slot with the last element and `pop`.

```js
const particles = [{ id: 1, life: 0.5 }, { id: 2, life: 0 }, { id: 3, life: 1.2 }, { id: 4, life: -0.1 }];
for (let i = particles.length - 1; i >= 0; i--) {   // backwards: the swapped-in element was already visited
  if (particles[i].life <= 0) {
    particles[i] = particles[particles.length - 1];
    particles.pop();
  }
}
console.log(particles.map(p => p.id));
```

When order matters (back-to-front draw order for transparency, a sorted list), compact in place with a write index: one pass, no allocation. One of the exercises is exactly that.

--- prompt
A scene is made of mesh parts, each `{ name, material, count, tris }`: `count` instances of a mesh with `tris` triangles each. Write `materialReport(parts)` returning one entry per `material`:

```js
{ material, parts, instances, totalTris, heaviest }
```

- `parts`: number of part entries using that material,
- `instances`: sum of `count`,
- `totalTris`: sum of `count * tris`,
- `heaviest`: the `name` of the part with the highest `count * tris` (on a tie, the one that appears first).

Parts with `count` of `0` or less are ignored entirely (a material with only such parts doesn't appear). Sort the result by `totalTris` descending, and by `material` alphabetically (plain `<` comparison) when equal. Don't modify `parts`.

This is the kind of report that tells you which material to batch first: every material is at least one draw call.
--- starter
function materialReport(parts) {
  return parts.map(p => ({ material: p.material }));
}
--- solution
function materialReport(parts) {
  const groups = Object.groupBy(parts.filter(p => p.count > 0), p => p.material);
  return Object.entries(groups)
    .map(([material, list]) => {
      let heaviest = list[0];
      for (const p of list) if (p.count * p.tris > heaviest.count * heaviest.tris) heaviest = p;
      return {
        material,
        parts: list.length,
        instances: list.reduce((s, p) => s + p.count, 0),
        totalTris: list.reduce((s, p) => s + p.count * p.tris, 0),
        heaviest: heaviest.name,
      };
    })
    .sort((a, b) => b.totalTris - a.totalTris || (a.material < b.material ? -1 : a.material > b.material ? 1 : 0));
}
--- hint
`Object.groupBy(parts.filter(...), p => p.material)` gives you `{ material: [parts] }`; `Object.entries` turns it into pairs to `map` over.
--- hint
For `heaviest`, a strict `>` comparison keeps the first of equal entries. Sort with `b.totalTris - a.totalTris || materialCompare`.

title: Leaderboard ranks
--- prompt
Shader variants are benchmarked: each run reports a `score` (higher is better) and a compile `time`. Write `rankScores(entries)` where entries are `{ name, score, time }`. Return a **new** array (don't sort the input in place) of `{ rank, name, score }` sorted by score descending, then time ascending (faster is better), then name ascending (`<` comparison).

Ranks use "competition ranking": entries with the same score **and** time share a rank, and the next rank skips accordingly (1, 2, 2, 4). Scores can be any numbers, including large ones and negatives, so make sure you sort numerically.
--- starter
function rankScores(entries) {
  return entries.sort().map((e, i) => ({ rank: i + 1, name: e.name, score: e.score }));
}
--- solution
function rankScores(entries) {
  const sorted = entries.toSorted((a, b) =>
    b.score - a.score || a.time - b.time || (a.name < b.name ? -1 : a.name > b.name ? 1 : 0));
  let rank = 0;
  return sorted.map((e, i) => {
    const prev = sorted[i - 1];
    if (!prev || prev.score !== e.score || prev.time !== e.time) rank = i + 1;
    return { rank, name: e.name, score: e.score };
  });
}
--- hint
`toSorted` with a comparator chained by `||`: `b.score - a.score || a.time - b.time || nameCompare`.
--- hint
Walk the sorted list; when an entry differs from the previous one in score or time, its rank is its index + 1, otherwise it inherits the previous rank.
--- harness

title: Parse a stencil mask
--- prompt
Procedural generators are often seeded from hand-drawn masks: where terrain may go, where to start growing. Write `parseMask(lines)` taking an array of equal-length strings and returning:

```js
{ width, height, cells, seeds, lights }
```

- `cells` is a **flat** array of length `width * height` (row-major, index `y * width + x`) containing `1` for a solid cell (`#`) and `0` for anything else.
- `seeds` is an array of `{ x, y }` for each `*` (a growth seed) in reading order.
- `lights` is the number of `o` characters.

Then write `cellAt(mask, x, y)` returning the cell at that position, or `1` (solid) for any position outside the mask, so neighbour lookups in a generator never need separate bounds checks ("clamp to border" addressing).

```js
const m = parseMask(['#####', '#*.o#', '#####']);
m.width          // 5
m.cells[6]       // 0   (x 1, y 1)
cellAt(m, -1, 0) // 1
```
--- starter
function parseMask(lines) {
  return { width: 0, height: 0, cells: [], seeds: [], lights: 0 };
}

function cellAt(mask, x, y) {
  return mask.cells[y][x];
}
--- solution
function parseMask(lines) {
  const height = lines.length, width = height ? lines[0].length : 0;
  const cells = new Array(width * height).fill(0);
  const seeds = [];
  let lights = 0;
  for (let y = 0; y < height; y++) {
    for (let x = 0; x < width; x++) {
      const c = lines[y][x];
      if (c === '#') cells[y * width + x] = 1;
      else if (c === '*') seeds.push({ x, y });
      else if (c === 'o') lights++;
    }
  }
  return { width, height, cells, seeds, lights };
}

function cellAt(mask, x, y) {
  if (x < 0 || y < 0 || x >= mask.width || y >= mask.height) return 1;
  return mask.cells[y * mask.width + x];
}
--- hint
Allocate the flat array once (`new Array(w * h).fill(0)`), then two nested loops write `cells[y * width + x]`.
--- hint
`cellAt` must check `x >= width` explicitly: with a flat array, `x = width` would silently read the first cell of the next row.
--- harness

=== exercise compact
title: Remove dead particles (fast)
--- prompt
Every frame, particles with `life <= 0` must be removed from the particle list. Write two functions that **modify the array in place** (same array object, no new array) and return the number removed:

- `removeDeadOrdered(list)`: keeps the survivors in their original order (they are sorted back to front for alpha blending).
- `removeDeadUnordered(list)`: order of survivors doesn't matter. Use swap-remove.

Both are tested with 300,000 particles, half of them dead, and must each finish in well under a second. Calling `splice` once per dead particle is O(n²) here and will fail the timing check. Don't allocate a new array either.
--- starter
function removeDeadOrdered(list) {
  let removed = 0;
  for (let i = 0; i < list.length; i++) {
    if (list[i].life <= 0) { list.splice(i, 1); i--; removed++; }
  }
  return removed;
}

function removeDeadUnordered(list) {
  return removeDeadOrdered(list);
}
--- solution
function removeDeadOrdered(list) {
  let w = 0;
  for (let r = 0; r < list.length; r++) {
    const e = list[r];
    if (e.life > 0) list[w++] = e;
  }
  const removed = list.length - w;
  list.length = w;
  return removed;
}

function removeDeadUnordered(list) {
  let removed = 0;
  for (let i = list.length - 1; i >= 0; i--) {
    if (list[i].life <= 0) {
      list[i] = list[list.length - 1];
      list.pop();
      removed++;
    }
  }
  return removed;
}
--- hint
Ordered: keep a write index `w`. For each survivor, `list[w++] = e`. At the end, truncate with `list.length = w`.
--- hint
Unordered: walk backwards; replace a dead element with the last one and `pop()`. Walking backwards means the element you swap in has already been checked.

=== exercise utils
title: range, chunk, zip, windows
--- prompt
Write four small utilities. Each returns a new array.

Everyday helpers for geometry code: `range` for sample positions, `chunk` to turn flat vertex data into triples, `zip` to pair positions with colors, `windows` for the segments of a line strip.

- `range(start, end, step = 1)`: numbers from `start` up to but excluding `end`. With a negative `step`, counts down to (excluding) `end`. If the range is empty, return `[]`. Throw a `RangeError` if `step` is `0`.
- `chunk(arr, size)`: split into consecutive pieces of `size` (the last may be shorter). Throw a `RangeError` if `size < 1`.
- `zip(...arrays)`: tuples of corresponding elements, as long as the **shortest** input. `zip()` is `[]`.
- `windows(arr, size)`: every run of `size` consecutive elements (sliding window). Fewer than `size` elements gives `[]`.
--- starter
function range(start, end, step = 1) {
  const out = [];
  for (let i = start; i < end; i += step) out.push(i);
  return out;
}

function chunk(arr, size) { return [arr]; }

function zip(...arrays) { return arrays; }

function windows(arr, size) { return [arr]; }
--- solution
function range(start, end, step = 1) {
  if (step === 0) throw new RangeError('step must not be 0');
  const n = Math.max(0, Math.ceil((end - start) / step));
  return Array.from({ length: n }, (_, i) => start + i * step);
}

function chunk(arr, size) {
  if (size < 1) throw new RangeError('size must be >= 1');
  return Array.from({ length: Math.ceil(arr.length / size) }, (_, i) => arr.slice(i * size, (i + 1) * size));
}

function zip(...arrays) {
  if (!arrays.length) return [];
  const n = Math.min(...arrays.map(a => a.length));
  return Array.from({ length: n }, (_, i) => arrays.map(a => a[i]));
}

function windows(arr, size) {
  return Array.from({ length: Math.max(0, arr.length - size + 1) }, (_, i) => arr.slice(i, i + size));
}
--- hint
All four are `Array.from({ length: n }, (_, i) => ...)` once you work out `n`. For `range` it's `ceil((end - start) / step)`, clamped at 0.
--- hint
`Math.min(...arrays.map(a => a.length))` for zip, but handle zero arrays first: `Math.min()` is `Infinity`.

--- q
A particle system removes dead particles each frame with `particles = particles.filter(p => p.life > 0)`. With 5,000 particles, what's the main cost compared to an in-place compaction?
--- choice
`filter` is O(n²).
--- answer
It allocates a new 5,000-slot array every frame, which becomes garbage the collector must reclaim.
--- choice

--- explain
`filter` is O(n) and keeps order, so it's correct and often fine. But it creates a fresh array each frame; at 60 fps that's steady garbage, and GC pauses cause frame hitches. A write-index compaction reuses the same array.
