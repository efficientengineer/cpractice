## The compute pipeline, again, slower

```text
shader module ──┐
                ├─ createComputePipeline({ layout, compute: { module, entryPoint, constants } })
pipeline layout ┘        │
  └ bind group layouts   └─ pass.setPipeline(p); pass.setBindGroup(0, bg); pass.dispatchWorkgroups(x, y, z)
```

`entryPoint` can be omitted when the module has exactly one compute entry point. A module can hold several (`fn clear`, `fn step`, `fn draw`), and each pipeline picks one.

## Bind group layouts: 'auto' vs explicit

With `layout: 'auto'`, WebGPU reads the shader and builds the bind group layouts for you; `pipeline.getBindGroupLayout(n)` returns them. It's convenient but has two traps:

- **An auto layout only fits its own pipeline.** A bind group made from pipeline A's auto layout can't be used with pipeline B, even if the shaders declare identical bindings.
- **Bindings the entry point doesn't use are left out.** If your shader declares `@binding(2)` but the code never reads it, the auto layout has no binding 2, and a bind group that provides one is a validation error.

An explicit layout fixes both. You describe each binding: its number, which stages see it, and what kind of resource it is:

```js
const device = await getDevice();
const layout = device.createBindGroupLayout({ entries: [
  { binding: 0, visibility: GPUShaderStage.COMPUTE, buffer: { type: 'read-only-storage' } },  // var<storage, read>
  { binding: 1, visibility: GPUShaderStage.COMPUTE, buffer: { type: 'storage' } },            // var<storage, read_write>
  { binding: 2, visibility: GPUShaderStage.COMPUTE, buffer: { type: 'uniform' } },            // var<uniform>
]});
const pipelineLayout = device.createPipelineLayout({ bindGroupLayouts: [layout] });
const module = device.createShaderModule({ code: `
@group(0) @binding(0) var<storage, read> src: array<f32>;
@group(0) @binding(1) var<storage, read_write> dst: array<f32>;
@group(0) @binding(2) var<uniform> scale: f32;
@compute @workgroup_size(64) fn double(@builtin(global_invocation_id) id: vec3u) {
  if (id.x < arrayLength(&dst)) { dst[id.x] = src[id.x] * scale; }
}
@compute @workgroup_size(64) fn negate(@builtin(global_invocation_id) id: vec3u) {
  if (id.x < arrayLength(&dst)) { dst[id.x] = -src[id.x]; }    // doesn't use scale
}` });
// Two pipelines, one layout: one bind group works with both.
const pDouble = device.createComputePipeline({ layout: pipelineLayout, compute: { module, entryPoint: 'double' } });
const pNegate = device.createComputePipeline({ layout: pipelineLayout, compute: { module, entryPoint: 'negate' } });
const mk = (size, usage) => device.createBuffer({ size, usage });
const src = mk(16, GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST);
const dst = mk(16, GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_SRC);
const uni = mk(16, GPUBufferUsage.UNIFORM | GPUBufferUsage.COPY_DST);
device.queue.writeBuffer(src, 0, new Float32Array([1, 2, 3, 4]));
device.queue.writeBuffer(uni, 0, new Float32Array([10]));
const bindGroup = device.createBindGroup({ layout, entries: [
  { binding: 0, resource: { buffer: src } }, { binding: 1, resource: { buffer: dst } }, { binding: 2, resource: { buffer: uni } }] });
for (const p of [pDouble, pNegate]) {
  const enc = device.createCommandEncoder(), pass = enc.beginComputePass();
  pass.setPipeline(p); pass.setBindGroup(0, bindGroup); pass.dispatchWorkgroups(1); pass.end();
  device.queue.submit([enc.finish()]);
  console.log(new Float32Array(await readBuffer(device, dst)));
}
```

Real engines use explicit layouts and organize bind groups by how often they change: group 0 for per-frame data (camera, time), group 1 for per-material, group 2 for per-object. Switching a bind group is cheap, but switching fewer is cheaper.

## Workgroups and invocation ids

`@workgroup_size(x, y, z)` sets the shape of one workgroup (missing dimensions are 1). `dispatchWorkgroups(X, Y, Z)` launches an X×Y×Z grid of them. Invocations in the same workgroup run together on one compute unit and can share `var<workgroup>` memory and synchronize with barriers; different workgroups can't talk to each other within a dispatch.

| Built-in | Type | Meaning |
|---|---|---|
| `local_invocation_id` | `vec3u` | position inside the workgroup, `0..workgroup_size-1` |
| `local_invocation_index` | `u32` | the same, flattened: `x + y*sx + z*sx*sy` |
| `workgroup_id` | `vec3u` | which workgroup in the dispatch grid |
| `global_invocation_id` | `vec3u` | `workgroup_id * workgroup_size + local_invocation_id` |
| `num_workgroups` | `vec3u` | the dispatch size you passed |

Default limits (`device.limits`): at most **256 invocations per workgroup** (`x*y*z`), at most 256×256×64 per dimension, **16 KiB** of workgroup memory, and at most **65535 workgroups per dimension** of a dispatch. For more than 65535 × 64 ≈ 4 million elements in 1D, dispatch a 2D grid and compute a flat index.

For 2D data (images, tile maps) use 2D workgroups like `@workgroup_size(8, 8)` (64 invocations) and `dispatchWorkgroups(ceil(w / 8), ceil(h / 8))`, and bounds-check both coordinates.

> **Performance:** 64 invocations per workgroup is the safe default (8×8 in 2D). Hardware runs invocations in groups of 32 or 64 lanes; a workgroup of 1 or 7 leaves most lanes idle, and the extra invocations of an oversized grid cost almost nothing when they exit at the bounds check. Go bigger (128, 256) only when shared memory algorithms benefit, and measure.

## Parallel map: one invocation per element

The simplest and most common pattern: each invocation reads its element, computes, writes its element. No invocation depends on another, so nothing needs synchronizing. A bullet system:

```js
const device = await getDevice();
const N = 100000;
// INIT (once): shader, pipeline, buffers, bind group.
const module = device.createShaderModule({ code: `
struct Params { dt: f32, width: f32, height: f32 }
@group(0) @binding(0) var<storage, read_write> pos: array<vec2f>;
@group(0) @binding(1) var<storage, read> vel: array<vec2f>;
@group(0) @binding(2) var<uniform> params: Params;
@compute @workgroup_size(64) fn main(@builtin(global_invocation_id) id: vec3u) {
  let i = id.x;
  if (i >= arrayLength(&pos)) { return; }
  var p = pos[i] + vel[i] * params.dt;
  let size = vec2f(params.width, params.height);
  p = p - floor(p / size) * size;            // wrap around the screen edges
  pos[i] = p;
}` });
const pipeline = device.createComputePipeline({ layout: 'auto', compute: { module } });
const pos = new Float32Array(N * 2), vel = new Float32Array(N * 2);
for (let i = 0; i < N; i++) {
  pos[i * 2] = Math.random() * 640; pos[i * 2 + 1] = Math.random() * 480;
  const a = Math.random() * Math.PI * 2;
  vel[i * 2] = Math.cos(a) * 200; vel[i * 2 + 1] = Math.sin(a) * 200;
}
const posBuf = device.createBuffer({ size: pos.byteLength, usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST | GPUBufferUsage.COPY_SRC });
const velBuf = device.createBuffer({ size: vel.byteLength, usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST });
const paramBuf = device.createBuffer({ size: 16, usage: GPUBufferUsage.UNIFORM | GPUBufferUsage.COPY_DST });
device.queue.writeBuffer(posBuf, 0, pos);
device.queue.writeBuffer(velBuf, 0, vel);
const bindGroup = device.createBindGroup({ layout: pipeline.getBindGroupLayout(0), entries: [
  { binding: 0, resource: { buffer: posBuf } }, { binding: 1, resource: { buffer: velBuf } }, { binding: 2, resource: { buffer: paramBuf } }] });
const params = new Float32Array([1 / 60, 640, 480, 0]);

// PER FRAME: one small upload, one pass. 60 frames here, then one readback to check.
for (let frame = 0; frame < 60; frame++) {
  device.queue.writeBuffer(paramBuf, 0, params);
  const enc = device.createCommandEncoder(), pass = enc.beginComputePass();
  pass.setPipeline(pipeline); pass.setBindGroup(0, bindGroup);
  pass.dispatchWorkgroups(Math.ceil(N / 64));
  pass.end();
  device.queue.submit([enc.finish()]);
}
const after = new Float32Array(await readBuffer(device, posBuf, 16));
console.log('bullet 0 moved from', pos[0].toFixed(1), pos[1].toFixed(1), 'to', after[0].toFixed(1), after[1].toFixed(1));
```

The bullets never come back to the CPU during the loop. In a real game the render pass would read `posBuf` directly as instance data (chapter on vertices).

## Reduction: workgroup memory and barriers

Summing an array (total gold, the number of live enemies, the max height) doesn't map one-to-one. The standard GPU approach is a **tree**: each workgroup loads 64 values into `var<workgroup>` memory, then repeatedly adds the upper half onto the lower half: 64 → 32 → 16 → ... → 1. That's 6 steps instead of 63 sequential adds, and each workgroup writes one partial sum.

```wgsl
var<workgroup> scratch: array<u32, 64>;

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) gid: vec3u,
        @builtin(local_invocation_id) lid: vec3u,
        @builtin(workgroup_id) wid: vec3u) {
  var v = 0u;
  if (gid.x < arrayLength(&data)) { v = data[gid.x]; }
  scratch[lid.x] = v;
  workgroupBarrier();                      // all 64 loads are done
  for (var stride = 32u; stride > 0u; stride /= 2u) {
    if (lid.x < stride) {
      scratch[lid.x] += scratch[lid.x + stride];
    }
    workgroupBarrier();                    // this level is done before the next reads it
  }
  if (lid.x == 0u) { partial[wid.x] = scratch[0]; }
}
```

**`workgroupBarrier()`** waits until every invocation in the workgroup reaches it, and makes their `var<workgroup>` writes visible to each other. Without it, an invocation could read `scratch[lid.x + stride]` before its neighbor wrote it: a data race, and wrong answers that change from run to run.

Two rules come with barriers:

- **Every invocation of the workgroup must reach the same barrier.** A barrier inside `if (lid.x < stride)` would deadlock or worse, so WGSL forbids it: the compiler's *uniformity analysis* rejects a barrier in control flow that depends on per-invocation values. Note how the loop above has a uniform trip count and the barrier sits outside the `if`.
- Barriers only synchronize *within a workgroup*. To combine partial sums from different workgroups, run a second dispatch (or sum the few partials on the CPU, or use atomics). Separate dispatches in a pass, and separate passes, see each other's storage writes in order.

## Atomics: a histogram

When many invocations update the same location, plain `+=` loses updates (two invocations read 5, both write 6). **Atomics** make read-modify-write indivisible:

```wgsl
@group(0) @binding(1) var<storage, read_write> bins: array<atomic<u32>, 16>;
// ...
atomicAdd(&bins[bucket], 1u);
```

`atomic<u32>` and `atomic<i32>` exist only in `storage` (read_write) and `workgroup` memory. Operations: `atomicLoad`, `atomicStore`, `atomicAdd`, `atomicSub`, `atomicMax`, `atomicMin`, `atomicAnd`, `atomicOr`, `atomicXor`, `atomicExchange`, `atomicCompareExchangeWeak`. On the JS side the buffer is just `u32`s.

Atomics on the same address serialize. With a million invocations hitting 16 bins, global atomics get slow; the fix is a per-workgroup histogram in `var<workgroup>` atomics, then one global `atomicAdd` per bin per workgroup:

```js
const device = await getDevice();
const module = device.createShaderModule({ code: `
@group(0) @binding(0) var<storage, read> damage: array<u32>;
@group(0) @binding(1) var<storage, read_write> bins: array<atomic<u32>, 8>;
var<workgroup> local: array<atomic<u32>, 8>;
@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) gid: vec3u, @builtin(local_invocation_index) li: u32) {
  if (gid.x < arrayLength(&damage)) {
    atomicAdd(&local[min(damage[gid.x] / 10u, 7u)], 1u);   // buckets 0-9, 10-19, ..., 70+
  }
  workgroupBarrier();
  if (li < 8u) { atomicAdd(&bins[li], atomicLoad(&local[li])); }
}` });
const pipeline = device.createComputePipeline({ layout: 'auto', compute: { module } });
const hits = new Uint32Array(10000).map((_, i) => (i * 37) % 90);
const hitBuf = device.createBuffer({ size: hits.byteLength, usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST });
device.queue.writeBuffer(hitBuf, 0, hits);
const binBuf = device.createBuffer({ size: 32, usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_SRC });
const enc = device.createCommandEncoder(), pass = enc.beginComputePass();
pass.setPipeline(pipeline);
pass.setBindGroup(0, device.createBindGroup({ layout: pipeline.getBindGroupLayout(0), entries: [
  { binding: 0, resource: { buffer: hitBuf } }, { binding: 1, resource: { buffer: binBuf } }] }));
pass.dispatchWorkgroups(Math.ceil(hits.length / 64)); pass.end();
device.queue.submit([enc.finish()]);
console.log(new Uint32Array(await readBuffer(device, binBuf)));
```

The barrier sits outside the bounds check (it must be reached by everyone), and workgroup memory starts zeroed in each workgroup.

## Prefix sum (scan)

An *inclusive scan* turns `[3, 1, 4, 1, 5]` into running totals `[3, 4, 8, 9, 14]`. It sounds serial, but it's one of the most useful parallel building blocks. The classic game use is **stream compaction**: given an `alive` flag per particle, the exclusive scan of the flags is each live particle's index in a packed output array, so a compute pass can remove dead particles without any CPU work. It also builds spatial hash grids (count per cell, scan, scatter).

The simple parallel scan within one workgroup (Hillis-Steele) runs `log2(n)` steps. At step `k` with `offset = 2^k`, every element adds the value `offset` positions to its left:

```text
start        3  1  4  1  5  9  2  6
offset 1     3  4  5  5  6 14 11  8
offset 2     3  4  8  9 11 19 17 22
offset 4     3  4  8  9 14 23 25 31
```

The trap: within a step, every invocation must *read* the old value before anyone *writes* the new one. So each step is read, barrier, write, barrier. Scans over more than one workgroup scan each block, scan the block totals, and add them back: three dispatches.

## Matrix multiply

`C = A × B` for n×n matrices: each output element is a dot product of a row of A and a column of B. One invocation per output element, on a 2D grid:

```wgsl
@compute @workgroup_size(8, 8)
fn main(@builtin(global_invocation_id) id: vec3u) {
  let row = id.y; let col = id.x;
  if (row >= n || col >= n) { return; }
  var sum = 0.0;
  for (var k = 0u; k < n; k++) { sum += a[row * n + k] * b[k * n + col]; }
  c[row * n + col] = sum;
}
```

This naive version reads every element of A and B `n` times from global memory. Fast implementations *tile*: each 8×8 workgroup loads 8×8 blocks of A and B into `var<workgroup>` memory, barriers, multiplies from shared memory, and repeats along k, cutting global reads by 8×. The same "load a tile into shared memory, then compute" pattern drives image blurs and other neighborhood operations.

## Timing and when the GPU wins

- **Overhead first.** Encoding, submitting and reading back costs tens to hundreds of microseconds regardless of size. For small arrays the CPU wins; the crossover is often around 10,000 to 100,000 elements, and depends heavily on how much work each element does.
- **Measure GPU work, not JavaScript.** `submit` returns instantly, so `performance.now()` around it measures nothing. Wait with `await device.queue.onSubmittedWorkDone()` (which includes some latency), or for precise numbers request the `'timestamp-query'` feature and write timestamps at the start and end of a pass.
- **Warm up.** The first run includes pipeline compilation and memory allocation. Time the second and later runs, and average many.
- **Keep data resident.** The win comes from leaving data on the GPU across many steps. Uploading, computing once and reading back is dominated by transfer.

```js
const device = await getDevice();
const module = device.createShaderModule({ code: `
@group(0) @binding(0) var<storage, read_write> d: array<f32>;
@compute @workgroup_size(64) fn main(@builtin(global_invocation_id) id: vec3u) {
  if (id.x < arrayLength(&d)) { d[id.x] = sqrt(d[id.x] * d[id.x] + 1.0); }
}` });
const pipeline = device.createComputePipeline({ layout: 'auto', compute: { module } });
const N = 1 << 20;
const buf = device.createBuffer({ size: N * 4, usage: GPUBufferUsage.STORAGE });
const bg = device.createBindGroup({ layout: pipeline.getBindGroupLayout(0), entries: [{ binding: 0, resource: { buffer: buf } }] });
async function run(times) {
  const enc = device.createCommandEncoder(), pass = enc.beginComputePass();
  pass.setPipeline(pipeline); pass.setBindGroup(0, bg);
  for (let i = 0; i < times; i++) pass.dispatchWorkgroups(Math.ceil(N / 64));   // many dispatches, one submit
  pass.end();
  device.queue.submit([enc.finish()]);
  await device.queue.onSubmittedWorkDone();
}
await run(1);                                   // warm-up
let t = performance.now(); await run(1);  const one = performance.now() - t;
t = performance.now();     await run(10); const ten = performance.now() - t;
console.log(`1 dispatch: ${one.toFixed(2)} ms, 10 dispatches in one submit: ${ten.toFixed(2)} ms`);
console.log('(numbers vary a lot by GPU; on software rendering they are slow)');
```

> **Performance:** record many dispatches into one pass and one submit rather than submitting each separately, and never read back inside the loop. Each `await` on the GPU idles one side while the other works.

  const module = device.createShaderModule({ code: `
    @group(0) @binding(0) var<storage, read_write> data: array<u32>;
    var<workgroup> s: array<u32, 256>;

    @compute @workgroup_size(256)
