## What you are walking into

You know C# and JavaScript. Most of C's *syntax* will feel familiar: braces, `if`, `for`, `while`, `switch`, the same operators. Its *model* is very different:

| | C# / JavaScript | C |
|---|---|---|
| Runtime | CLR / JS engine, GC, JIT | none: compiled to native machine code |
| Memory | managed, garbage collected | you `malloc` and `free` it yourself |
| Objects | classes, methods, interfaces | `struct`s and functions that take pointers to them |
| Strings | immutable string objects | arrays of `char` ending in a `0` byte |
| Errors | exceptions | return codes, `errno`, or crashing |
| Bounds checks | always | never |
| Generics | yes | `void *`, macros, or copy-paste |
| Bugs | usually an exception | often *undefined behavior*: anything can happen, including "seems to work" |

That last row is the important one. In C# reading past the end of an array throws. In C it reads whatever memory happens to be there, and the program carries on. Half of learning C is learning which things are your job now.

## The build pipeline

A C program goes through four stages. `gcc` runs them all for you:

1. **Preprocess**: handle `#include` and `#define` (pure text substitution). `gcc -E main.c` shows the result.
2. **Compile**: C to assembly, one `.c` file at a time. Each file is a *translation unit* and is compiled knowing nothing about the others.
3. **Assemble**: assembly to an object file (`.o`).
4. **Link**: glue the object files and libraries into an executable. "undefined reference to `foo`" is a linker error: something was declared but never defined.

On your own machine:

```text
gcc -std=c17 -Wall -Wextra -g main.c -o main
./main
```

Always use `-Wall -Wextra`. C compilers accept a lot of dubious code silently unless you ask for warnings.

## Hello, world, dissected

```c
#include <stdio.h>   // declarations for printf, puts, scanf, FILE...

int main(void) {     // (void) means "no parameters"; () means "unspecified" in older C
    printf("Hello, %s! %d + %d = %d\n", "C", 2, 3, 2 + 3);
    return 0;        // exit code: 0 means success
}
```

- `#include <stdio.h>` pastes in the header text. Headers mostly contain *declarations*: they tell the compiler that `printf` exists and what its signature is. The code itself lives in the C library, which the linker adds.
- `main` returns an `int` that becomes the process's exit code. Reaching the end of `main` without `return` returns 0 (only `main` gets that special case).
- There is no namespace, no class wrapping it. Functions are top level.

## printf in five minutes

`printf` takes a format string and a variable number of arguments. The compiler cannot fully check that they match (gcc warns with `-Wall`), and a mismatch is undefined behavior.

| Specifier | Type | Example output |
|---|---|---|
| `%d` / `%i` | `int` | `-42` |
| `%u` | `unsigned int` | `42` |
| `%ld`, `%lld` | `long`, `long long` | `123456789012` |
| `%zu` | `size_t` (result of `sizeof`) | `8` |
| `%f`, `%.2f` | `double` (and `float`, which is promoted) | `3.141593`, `3.14` |
| `%e`, `%g` | `double`, scientific / shortest | `3.141593e+00`, `3.14159` |
| `%c` | `char` (passed as `int`) | `A` |
| `%s` | `char *` string | `hello` |
| `%p` | `void *` pointer | `0x7ffd5c3e1a2c` |
| `%x`, `%X`, `%o` | `unsigned`, hex / octal | `ff`, `FF`, `377` |
| `%%` | a literal percent sign | `%` |

Width and flags go between the `%` and the letter: `%5d` pads to 5 columns on the left, `%-5d` pads on the right, `%05d` pads with zeros, `%8.3f` is 8 wide with 3 decimals, `%+d` always shows the sign.

```c
#include <stdio.h>

int main(void) {
    printf("[%5d] [%-5d] [%05d] [%+d]\n", 42, 42, 42, 42);
    printf("[%8.3f] [%-8.2f] [%.0f]\n", 3.14159, 2.5, 2.5);
    printf("[%x] [%X] [%#x] [%o]\n", 255, 255, 255, 8);
    printf("[%10s] [%-10s] [%.3s]\n", "right", "left", "truncate");
    printf("[%c%c%c] [%%]\n", 'C', 'a', 't');
    return 0;
}
```

`puts("text")` prints a string plus a newline. `putchar('x')` prints one character.

> **Performance:** `printf` parses its format string at runtime on every call, and output to a terminal is line buffered, so every `\n` can mean a system call. A `printf` per entity per frame will eat your frame budget on its own. Keep printing out of per-frame code (log on events, or once a second), and when you must format every frame (a HUD), format into a reused buffer and only when the value changed.

## Reading input

`scanf` is the mirror of `printf`, but it needs *addresses* of the variables to fill in, hence the `&`. It returns how many items it successfully read, which is how you detect bad input or end of file.

```c
#include <stdio.h>

int main(void) {
    int a, b;
    if (scanf("%d %d", &a, &b) != 2) {
        printf("expected two numbers\n");
        return 1;
    }
    printf("%d\n", a + b);
    return 0;
}
```

In the playground, type input into the **stdin** box. We will cover `scanf`'s many traps and safer alternatives (`fgets` + `sscanf`/`strtol`) in the I/O chapter.

## Declare before use

The compiler reads top to bottom. A function must be *declared* before it is called. Either define it above `main`, or write a *prototype* first:

```c
#include <stdio.h>

int square(int x);           // prototype (declaration)

int main(void) {
    printf("%d\n", square(7));
    return 0;
}

int square(int x) {          // definition
    return x * x;
}
```

## How this site runs your code

Your code is sent to the [Compiler Explorer](https://godbolt.org) API (with [Wandbox](https://wandbox.org) as a fallback) and compiled with gcc as:

```text
gcc -std=c17 -Wall -Wextra -g -O0 -fsanitize=address,undefined
```

The `-fsanitize` part turns on **AddressSanitizer** and **UndefinedBehaviorSanitizer**. They add runtime checks so that many silent C bugs (buffer overruns, use after free, signed overflow, leaks) crash loudly with a report instead. Real C programmers use them constantly during development; so will you. You can switch them off in the settings to see what "normal" C does with your bug.

There are two kinds of exercise:

- **Program** exercises: write a whole program. It is run with the given stdin and its output must match exactly (trailing spaces ignored).
- **Function** exercises: write one or more functions. Hidden test code (you can view it) calls them and checks the results. You may keep a `main` of your own for experimenting; it is renamed out of the way when the tests run.

Shortcuts: **Ctrl+Enter** runs, **Ctrl+Shift+Enter** checks against the tests.

> **Performance:** `-O0` with sanitizers is the right setting for *finding bugs*, and the wrong one for *measuring speed*: code here runs several times slower than an optimized build. When you care how fast something is, build with `gcc -O2` (and no sanitizers) on your own machine and measure before and after; never guess. Some exercises here have large-input tests with a 10 second limit. Those are not checking micro-optimizations; they fail a solution that does the wrong *amount* of work (an O(n²) loop where O(n) was possible), which no optimizer can save.

## Thinking like a game programmer

The examples and exercises lean toward game code: health and damage, tile maps, entities, particles, inventories. A game is a loop that must finish all its work in a fixed **frame budget**: 16.7 ms at 60 frames per second, 6.9 ms at 144. That budget shapes the habits this course teaches from the start:

- **Do the expensive work once, outside the loop**: allocate memory at load time, convert units when data is loaded, look up names once and keep the result.
- **Keep data contiguous**: arrays of plain values, walked in order, are what CPUs are fastest at.
- **Count the work**: an O(n²) loop over 10,000 entities is 100 million steps, every frame.
- **Measure** before optimizing, with an optimized build.

Notes marked **Performance** throughout the chapters point out the cheap way to do things and the habits to avoid.

This one is a **function** exercise: there is no `main` to write. Hidden tests call your functions; click **Tests** to see them.

--- solution

}

double average(int a, int b) {
    return ((double)a + b) / 2;
}
--- harness
int main(void) {
    CHECK_INT(add(2, 3), 5);

=== exercise hud
title: A HUD line
--- prompt
Games print a lot of fixed-width text: HUDs, debug overlays, log lines. Fixed widths keep the numbers from jittering left and right as they change.

Read `hp max_hp gold x y` from stdin (three `int`s, then two `double`s) and print one line:

For input `45 100 120 3.5 -2.25`:


If the input does not contain all five values, print `bad input` and exit with code 1.
--- starter
#include <stdio.h>

int main(void) {

int main(void) {

=== exercise ticks
title: Seconds to ticks
--- prompt
Most games run their simulation at a **fixed tick rate** (say 60 updates per second) no matter how fast frames are drawn. Game logic then counts in integer *ticks*, not floating-point seconds: integers never drift, two runs with the same input give the same result (replays, networking), and comparing `int`s is exact. Designers still think in seconds, so you convert once, when the data is loaded.

Write:

- `int seconds_to_ticks(double seconds, int tick_rate)`: the number of ticks closest to `seconds` (round halves up). `seconds` and `tick_rate` are never negative. `seconds_to_ticks(0.5, 60)` is 30, `seconds_to_ticks(0.1, 60)` is 6, `seconds_to_ticks(1.0 / 120, 60)` is 1 (0.5 rounds up).
- `double tick_ms(int tick_rate)`: how many milliseconds one tick lasts, so `tick_ms(60)` is about 16.667. This is your **frame budget**: everything the game does per tick has to fit in it.

The next exercise builds on these.
--- starter
int seconds_to_ticks(double seconds, int tick_rate) {
    return 0;
}

double tick_ms(int tick_rate) {
    return 0;
}
--- solution
int seconds_to_ticks(double seconds, int tick_rate) {
    return (int)(seconds * tick_rate + 0.5);
}

double tick_ms(int tick_rate) {
    return 1000.0 / tick_rate;
}
--- hint
Converting a `double` to `int` truncates toward zero. For non-negative values, adding `0.5` first turns truncation into rounding.
--- hint
`1000 / tick_rate` is integer division: 16, not 16.667.
--- harness
int main(void) {
    CHECK_INT(seconds_to_ticks(0.5, 60), 30);
    CHECK_INT(seconds_to_ticks(0.1, 60), 6);
    CHECK_INT(seconds_to_ticks(1.0 / 120, 60), 1);
    CHECK_INT(seconds_to_ticks(0.0, 60), 0);
    CHECK_INT(seconds_to_ticks(2.0, 30), 60);
    CHECK_INT(seconds_to_ticks(0.004, 60), 0);
    CHECK_INT(seconds_to_ticks(90.0, 144), 12960);
    CHECK_DBL(tick_ms(60), 1000.0 / 60);
    CHECK_DBL(tick_ms(144), 1000.0 / 144);
    CHECK_DBL(tick_ms(1000), 1.0);
    return TEST_END();
}

=== exercise cooldown
title: Ability cooldowns
continues: ticks
--- prompt
Keep your two functions and add cooldowns, measured in ticks. An ability used at tick `last_used` with a cooldown of `cooldown` ticks is ready again at tick `last_used + cooldown`.

- `int cooldown_left(int now, int last_used, int cooldown)`: how many ticks until the ability is ready, or 0 if it is ready now.
- `int cooldown_ticks(double seconds, int tick_rate)`: the designer gives cooldowns in seconds; convert with your `seconds_to_ticks`, but never return less than 1 tick (a cooldown of 0 would let the ability fire every tick, which designers never mean).

Notice the shape: store the *tick it was used*, not a countdown you decrement every frame. Nothing needs updating per frame, and checking costs one subtraction.
--- stubs
int cooldown_left(int now, int last_used, int cooldown) {
    return -1;
}

int cooldown_ticks(double seconds, int tick_rate) {
    return -1;
}
--- solution
int seconds_to_ticks(double seconds, int tick_rate) {
    return (int)(seconds * tick_rate + 0.5);
}

double tick_ms(int tick_rate) {
    return 1000.0 / tick_rate;
}

int cooldown_left(int now, int last_used, int cooldown) {
    int left = last_used + cooldown - now;
    return left > 0 ? left : 0;
}

int cooldown_ticks(double seconds, int tick_rate) {
    int t = seconds_to_ticks(seconds, tick_rate);
    return t < 1 ? 1 : t;
}
--- hint
`last_used + cooldown - now` can be negative once the cooldown is over: clamp it to 0.
--- harness
int main(void) {
    CHECK_INT(cooldown_left(100, 100, 30), 30);
    CHECK_INT(cooldown_left(110, 100, 30), 20);
    CHECK_INT(cooldown_left(129, 100, 30), 1);
    CHECK_INT(cooldown_left(130, 100, 30), 0);
    CHECK_INT(cooldown_left(5000, 100, 30), 0);
    CHECK_INT(cooldown_ticks(0.5, 60), 30);
    CHECK_INT(cooldown_ticks(0.0, 60), 1);
    CHECK_INT(cooldown_ticks(0.001, 60), 1);
    CHECK_INT(cooldown_ticks(2.5, 20), 50);
    CHECK_INT(seconds_to_ticks(0.5, 60), 30);
    return TEST_END();
}

=== exercise budget
title: Frame budget report
--- prompt
A profiler says how long each system took this frame. Read the target frame rate `fps` and a count `n`, then `n` lines of `name milliseconds`. Print the budget, one line per system with its share of the budget, and a total line:

```text
60 3
physics 4.2
ai 6.1
render 7.5
```

gives

```text
budget 16.67 ms
physics    4.20 ms  25.2%
ai         6.10 ms  36.6%
render     7.50 ms  45.0%
total     17.80 ms  OVER by 1.13 ms
```

- Names are left aligned in 8 columns, times are `%7.2f`, the share is `%5.1f` followed by `%`. The share is `100 * ms / budget`.
- The last line is `total` in 8 columns, the summed time as `%7.2f ms`, then two spaces and either `OVER by X ms` (if the total is above the budget, `X` with 2 decimals) or `ok, X ms spare`.

Names are at most 15 characters. Read each with `scanf("%15s %lf", name, &ms)`: the `15` stops `scanf` from writing past the 16-byte array.
--- starter
#include <stdio.h>

int main(void) {
    int fps, n;
    if (scanf("%d %d", &fps, &n) != 2) return 1;
    char name[16];
    double ms;
    // print the report
    return 0;
}
--- solution
#include <stdio.h>

int main(void) {
    int fps, n;
    if (scanf("%d %d", &fps, &n) != 2) return 1;
    double budget = 1000.0 / fps, total = 0;
    printf("budget %.2f ms\n", budget);
    char name[16];
    double ms;
    for (int i = 0; i < n; i++) {
        if (scanf("%15s %lf", name, &ms) != 2) return 1;
        total += ms;
        printf("%-8s%7.2f ms %5.1f%%\n", name, ms, 100 * ms / budget);
    }
    if (total > budget)
        printf("%-8s%7.2f ms  OVER by %.2f ms\n", "total", total, total - budget);
    else
        printf("%-8s%7.2f ms  ok, %.2f ms spare\n", "total", total, budget - total);
    return 0;
}
--- hint
`1000.0 / fps` is the budget in ms. A literal `%` in a format string is `%%`.
--- hint
Keep a running `total` while you print the rows; you don't need to store them.
--- test

physics 4.2
ai 6.1
render 7.5
--- out

physics    4.20 ms  25.2%
ai         6.10 ms  36.6%
render     7.50 ms  45.0%
total     17.80 ms  OVER by 1.13 ms

update 10
draw 12.5
--- out
